Preface

Triad is a standalone programming language: block syntax and declared types, multiple dispatch, integrated logic programming, code as data. Its definition is a normative specification independent of the implementation, accompanied by an executable specification and a conformance suite with verifiable golden tests. This book is the study path.

The book arises from a simple need: learning Triad does not mean just reading the specification, but building a mental model of the language, its constructs, and its runtime. The specification is normative and precise, but it is written to be implemented, not to be read like a novel. This volume translates it into a path: explanations, examples, exercises, profile markers. The explanations, examples, and exercises gradually build the mental model of the language. The specification remains the normative reference source, not a reading prerequisite.

The ideal reader already knows how to program in another language: knows what a variable is, a function, a loop, a recursion. This book does not teach programming in general, it teaches Triad. The language's influences (Julia, Prolog, Lisp) are documented in Appendix A of the specification: they are informative notes, not definitions. Triad is not a dialect of any of the three.

The volume brings together two complementary and independent texts. The Triad 2.0 Manual explains the language, proposes exercises, and closes with grammar, quick reference cards, error table, glossary, and appendices. The Triad 2.0 Tutorial is divided into five parts: first steps, Triad-Core, Triad-Full, project code, and reference. You can read the Manual in full without the Tutorial, and the Tutorial in full without the Manual: each explains what it needs. The index that follows collects the chapters of both texts, so they can be found in one place.

If you want to write executable programs today, start with the Tutorial, parts I and II; use the Manual to deepen concepts and do exercises. To study the complete standard, continue with part III of the Tutorial and the corresponding chapters of the Manual. Part IV is for those who want to explore or modify the repository.

The Manual's appendices guide through the language's influences and the project's sources. The full normative texts are not reproduced in the volume: those who want formal detail find them in the SPEC.md and SPEC-CORE.md files of the repository, which remain the definitive sources in case of divergence. The volume nevertheless contains the rules necessary to understand and use the language: the reference to the specification is a deepening, not a dependency.

Two conformance profiles run through the whole book. Triad-Core is the bootstrap subset: values, functions, closures, control flow, lists, strings, I/O. Triad-Full is the complete standard. Every Core program is also a valid Full program and must behave the same way. The [Core] and [Full] markers indicate in which profile each construct exists; the code blocks are marked triad for Core code and triad-full for code defined by the Full standard, not yet executable by the current runtime. Core examples can be tried with the reference JavaScript interpreter (node seed/dev/triad_core.cjs); fragments indicated as seed-specific are exceptions.

The S0 seed is a Triad-Core interpreter written directly in x86-64 machine code, without a host language; today the executable seed is the one for Windows. It should not be confused with the JavaScript interpreter used to run Core examples and verify conformance. The bootstrap plan provides S1 (a Triad interpreter written in Triad-Core), S2 (native compiler), S3 (self-hosting) and S4 (cross-platform parity). Where the runtime does not cover a construct, the text says so explicitly.

Happy reading, and happy coding.

— GPuntobit

Triad 2.0 Handbook

The complete manual of the language: vocabulary, values, flow control, functions, dispatch, logic, code as data, errors, contracts, budgets, tracks, effects, exercises and reference.

Triad is a self-contained programming language: block syntax and declared, multiple types dispatch, integrated logic programming and code as data, in a single syntax. His definition is a specific regulation independent of any implementation (SPEC.md, standard 0.2.0), accompanied by an executable specification (SPEC-CORE.md) and a conformance suite with verifiable goldens (conformance/).

This manual teaches the language as it is defined by the standard. It is not a summary of specification: it is a study path, with explanations, examples and exercises. You can read it from the beginning at the end without any other material: every concept needed to understand a chapter is explained first or in that chapter, and the external references are optional further information. It is not a collection of pages to be consulted at random: it is a book, and the order of the chapters builds the mental model of language one piece at a time.

How to read this manual

Who is it addressed to?

You know how to program, in any language: you know what a variable, a function, a loop, a recursion. This manual does not explain programming in general, Triad explains.

The manual doesn't assume you've read anything else: every concept is explained where it matters. I project regulatory documents — SPEC.md, SPEC-CORE.md — and the compliance suite in conformance/ are the texts and tests that you can go back to for further information or to check a extreme case, but they are not prerequisites: they are the reference for those who want to verify, not the manual of those who want to learn. For this reason the text always distinguishes what is a rule of language from what is which is behavior of a particular implementation.

Two profiles, one language

The standard defines two compliance profiles, and it is useful to know how to distinguish them before starting:

| profile | what does it contain | where | is defined |---|---|---| | Triad-Core | values, functions, closures, flow control, lists, strings, I/O | SPEC-CORE.md | | Triad-Full | everything: declared types, dispatch, logic, macros, contracts, budgets, tracks, effects | SPEC.md |

Triad-Core is a subset of Triad-Full: every Core program is also a Full program valid and must behave in the same way. The manual presents the two profiles on the same level, by logical construction: each chapter introduces a construct and says in which profile it exists. Not because Full is "further ahead", but because they are two sides of the same specification.

The Core profile is not a simplified version for educational convenience: it is the chosen subset why a bootstrap interpreter, written in a few thousand lines, can run it, and why it same language can describe itself. Full adds constructs that require a more engine rich — multiple dispatch, unification, macro expansion — but it doesn't change the meaning of the ones Core already has. Learning Core, therefore, is not time spent on a different language.

Where the difference matters, you find two markers:

  • [Core] — the construct exists in the bootstrap subset;
  • [Full] — the construct exists only in the full standard.

A profile marker describes what the standard defines, not what each program does installed already knows how to run. For this reason the manual distinguishes three levels: the normative rule (what the construct should mean), availability in the Core or Full profile and the status of the implementations present in the repository. A Full example can be corrected according to the standard and, at the same time, not yet be executable by the current runtime. When a example reports Output (golden Full), the result is an expected value preserved by the suite, not a check just performed by a complete Full interpreter.

To study a construct without confusing these levels, ask yourself in order: what form do you accept grammar? What values ​​does it read and produce? What effects or errors can it generate? in which one Is profile defined? which implementation and which conformance case verify this? This one sequence allows you to move from code to semantics and then to proofs, instead of dealing the output of a single runtime as the language definition.

The example shows three things that are true throughout the book. The shebang is just a convenience of the systems operations: the parser skips it, so the program actually starts from the second line. println It doesn't put separators between arguments, so the comma and space you see in the output are characters written in the program, not automatic formatting. Finally 6 * 7 is calculated before printing: The arguments of a call are expressions, not text. Past topics from the command line (one, two) do not become variables with those names: they all end up in the list ARGS, as explained in chapter 20.

Part I — Language

The first part builds the language layer by layer: first the building blocks (lexicon and values), then the expressions and flow control, then the functions and calculation models that Triad adds — dispatch, closures, logic, code as data — and finally the tools with which a program communicates with the outside (errors, contracts, budget, tracks, effects). Every chapter yes relies on precedents; the examples are short on purpose, because the point is not to admire a program but understand one rule.

1. Vocabulary

1.1 Identifiers

An identifier begins with a letter or _, followed by letters, digits, or _. A final ! is allowed if not followed by =. [Core]

x = 1
sum_2 = 2
_ = 3
valid_name = 4

push!, sort! and similar are legitimate names: the final ! convention is for functions that they change their topic (chap. 9).

The ! does not change the meaning of the name and is not an operator: it is a signal to the reader. The parser accepts it only as the last character, and only if the following character is not =; otherwise a confrontation would begin. This is the first of the conventions that Triad inherits from Julia: the name declares a contract, but the programmer must respect it.

In Triad-Full identifiers also allow non-ASCII letters. [Full]

age = 42

1.2 Numbers

Integers are written with decimal places; _ works as a separator. The sign is an operator unary, not part of the literal. [Core]

The distinction is more important than it seems: -5 is the application of the - operator to literal 5, not a negative number written in a special way. That's why there isn't one "negative syntax" to remember: the parentheses and precedence levels from chapter 4 already explain what happens in an expression like -x * y.

println(42)
println(1_000_000)
println(-5)

Output:

42
1000000
-5

Float exists only in Triad-Full. [Full]

println(3.14)
println(1e-9)

1.3 Strings

A string is an immutable sequence of UTF-8 bytes, enclosed in double quotes. Escapes are \n, \t, \", \\. [Core]

println("hello\n")
println("tab:\t|")
println("quotes: \"")
println("backslash: \\")

Output:

hello

tab: |
quotes: "
backslash:\

In Core there is no interpolation: "x = $x" literally prints x = $x. In Full exists, and you write $x for a simple expression and $(expr) for a complex one. [Full]

x = 42
println("x = $x")
println("x + 1 = $(x + 1)")

1.4 Symbols

A symbol is : followed by a name or operator: :alice, :+. Two symbols are equal if they have the same name. In Triad-Full the symbol is also the atom of logic (chap. 16). [Core]

A symbol serves to give a stable name to a thing — a category, a key, an atom — without the flexibility and the cost of a string. The difference compared to a string is not just one of convenience: :alice is an identity, "alice" is a sequence of bytes; two symbols with the same name are lo same value wherever they appear, while two strings must be compared character by character. It is this property that makes the symbols suitable for record keys (chap. 2), list tags and to the atoms of facts (chap. 16).

println(:alice)
println(:+)
println(:ok == Symbol("ok"))

Output:

alice
+
true

1.5 Comments

# comments to end of line. #= … =# comments on multiple lines; the standard describes this shape but doesn't dictate that block comments are nested, and the reference interpreter closes at first =#: Don't rely on nesting. [Core]

#= comment
   on multiple lines =#
x = 1_000 # line comment
println(x)

Output:

1000

1.6 Separators and line endings

A statement ends with a newline or ;. Newlines close a statement, except inside ( ), [ ], and :( ), and except immediately following a binary operator or a rule comma.

println(1); println(2)

A practical consequence: in Triad-Core each newline closes the statement. Core's grammar does not have a line continuation rule: an expression split across multiple lines is not a valid program. Write one statement per line and use ; to separate two statements.

total = 1 + 2 + 3
println(total);
println("second statement")

Output:

6
second education

The rule has a consequence on formatting: when you want to break a long expression, the parentheses are not enough in Core. The reference interpreter ends the statement at the first line break too inside a call, so println(1 + and 2) on different lines is not a valid program today. For the code intended for the current runtime only one rule applies: one statement per line, and ; only when two instructions must be on the same line.

In Triad-Full the rule is more permissive: SPEC §1 states that a newline doesn't close the statement inside ( ), [ ] and :( ), nor immediately after a binary operator. The interpreter of current reference does not yet implement this exception, so even in Full the form safe remains one instruction per line.

1.7 The rule of the colon and the question mark

: has three meanings and ? has two. The specification explicitly calls them “the classical problem of :» — is the first point where Triad deviates from the syntax you know.

writing meaning
1:n, xs[2:end] : attached to a value and without spaces → range
f(:a), x = :a : not preceded by a value and followed by a name → symbol
:( … ) → listed code
c ? a : b : surrounded by spaces → ternary separator
writing meaning
?x ? attached → logical variable
? ? with space after → ternary

Hence the rule of thumb: when : is ambiguous, add or remove spaces. xs[2:end] is a range; c ? a : b is a ternary because the two spaces surround it.

The two tables look like a list of special cases, but they stem from a single idea: a character adhering to the previous token belongs to that token, a separate one belongs to the syntax. This is why in Triad spacing is not a question of style: it is information that the parser reads. If write xs[2: end] or a ? b:c, changing the spaces does not change the appearance of the program: you change what the parser recognizes, and most of the time you get a syntax error. The advice is always write the spaces that make the meaning explicit.

1.8 Keywords

The standard defines 29 keywords:

function struct macro end if elseif else for in while let begin return
break continue fact rule solve quote try catch with requires ensures
true false nothing is

And 4 contextual words, valid only after solve:

limit depth steps trace

true, false and nothing are values, not structural words.

Keywords are reserved because the parser must recognize them before knowing what they are doing: if if could also be a variable name, reading a line would depend on the context in an unpredictable way. true, false and nothing are exceptions only in appearance: they are values that the language predefines, not syntactic forms. The four contextual words show the same principle in reverse: limit, depth, steps and trace are very normal names as long as they do not follow solve, and only there do they have a special meaning. This distinction reduces the number of reserved words and allows you to use natural names in the rest of the program.

1.9 Advanced identifiers and conventions

In Triad-Core identifiers are limited to ASCII: letters, digits, and _. In Triad-Full yes they also allow non-ASCII letters (accented, Greek, Cyrillic): age, π, Δx are names valid. [Full]

age = 42
π = 3.14159
Δx = 0.001
println(age + π)

The trailing ! convention (push!, sort!) indicates functions that mutate their argument. It is the only special character allowed inside an identifier: the grammar accepts letters, digits, _ and the final !, and nothing more. In particular the ? is not part of the name, because in Triad introduces a logical variable or ternary: valid? is not a valid identifier. For a predicate uses a normal name and lets the Bool type of the result tell what it is — empty, is_valid. [Core]

function push!(xs, v)
    # mutates xs and returns it
    xs
end

function empty(xs)
    length(xs) == 0
end

The body of push! is intentionally empty here: the example is about names, not implementation. The True mutation of lists, with push! and with assignment to an element, is in chapter 9.

Identifiers that match a keyword are not allowed: function, end, if cannot be used as variable or function names. [Core]

1.10 Escape and advanced strings

The standard sets four escapes in strings: \n, \t, \", \\; in Triad-Full it is added \$, because the $ introduces interpolation and must be neutralized when it must remain a character normal. The extended forms \r, \0, \u{…} and \x{…} that appear in the following fragment are not listed in SPEC §1: treat them as extensions of a single implementation, not as guarantees of language. A portable program uses documented escapes. [Full]

println("a\r\nb") # carriage return CRLF
println("unicode: \u{1F600}") # emoji
println("hex: \x{41}") # 'A'

A string is a sequence of UTF-8 bytes and strings are immutable: any operation of concatenation creates a new string, as shown in the example below. Length is measured in bytes and not in characters, a detail that matters as soon as you leave the Latin alphabet (chap. 10). [Core]

a = "hello"
b = a * "world"
println(a) # "hello" — unchanged
println(b) # "hello world"

Output:

hello
hello world

2. Values and types

2.1 The types

A Triad value always belongs to a type, and the type can always be observed: the table lists the types of the standard, with the name that typeof returns and the profile in which they exist.

type values ​​ typeof(v)
Int 64-bit signed integers, wrapped arithmetic Int
Float floating point numbers [Full] Float
Bool true, false Bool
String immutable UTF-8 byte sequence String
Symbol :name Symbol
List mutable heterogeneous list, indices of 1 List
Function named function, lambda, builtin Function
Nothing nothing Nothing
Expr quoted code [Full] Expr
Term, LVar logical terms and variables [Full] —
Solution {who = :dave} [Full] —
Err error as given [Full] —
Type the types themselves are [Full] values —
struct user Point(3.0, 4.0) [Full] Point

The Core type set is closed and small: Int, Bool, String, Symbol, List, Function, Nothing. In Core there are no Float, Term, Solution, Err as language values: a error is a list tagged [:Err, kind, msg] (ch. 11) and a struct is [:Point, x, y]. The set closed is not an arbitrary limitation: a bootstrap interpreter must be able to represent every value with few structures, and the Full concepts that are missing — error, struct, solution — yes they reconstruct by convention on lists and symbols.

typeof returns the type name as symbol. Profile detail matters: in Core the result is a Symbol, so typeof(1) == :Int is the natural comparison; in Triad-Full the types are values of type Type, so typeof(3) == Int compares directly to the type. The press is there same (Int), but the operation you write is different — which is why the table above has a column typeof(v) with the name and not the type.

It's helpful to separate three ideas that may seem like the same thing in syntax. The value is the concrete data, for example 5 or "hello"; the dynamic type describes the category of the value that the program is manipulating; a declared constraint instead restricts which values it can take on a name or parameter. In Core the type is observed with typeof, but it is not declared variable like x::Int. In Full the types also enter signatures, structs and dispatch. A conversion like Float(3) constructs a compatible value; an assertion like x::Int checks a value already obtained. They are different operations: converting can change the value, assert is not a request for conversion.

Another important distinction is between nominal type and structural form. In Full one struct Point declares a type identity, so a Point value does not become another type just because it has similar fields. In Core, where there are no structs, the same information is conventional: a list like [:Point, 3, 4] carries the :Point tag and fields in positions agreed by the program. The tag makes it possible to recognize the record, but does not add itself field controls, immutability or dispatch.

xs = [1, :a, "s"]
println(typeof(1), " ", typeof("s"), " ", typeof(:a), " ", typeof(xs))
println(typeof(nothing), " ", typeof(true), " ", typeof(x -> x))

Output:

2.7 Conditions accept only Bool

3. Variables and assignment

name = expr binds or updates a name. The assignment is an expression and is the value assigned. +=, -=, *= update an existing variable and evaluate the left side a only once. Using a name that was never assigned is an execution error. [Core]

The = sign does not read "write to memory": it binds a name to a value. When the name doesn't exist it creates it, when it exists it replaces the bond. Triad does not distinguish the two cases with keywords different and does not have a word to declare a variable: let introduces a scope, it does not declare a type. This simplicity has a price that should be known immediately: a poorly written name doesn't work reported as you write, but only when that line is executed.

x = 42
y = x + 8
x = x + 1
z = (x + y) * 2
println(x, " ", y, " ", z)

n -= 3
n *= 2
println(n)

Output:

43 50 186
24

There are no declarations: variables are dynamic. The visibility rules can be seen in the chapter 8.

Why would an assignment have a value? Because in Triad everything that can appear in a program is an expression, and assignment is no exception: so x = 42 can fit inside a if, a let, or a function argument without special syntax. The value is the one assigned, not a successful Bool like in other languages; that's why you won't write if x = 5 expecting it a check, because 5 is not a Bool and the condition fails with a type error.

+=, -= and *= are also expressions and take the updated value. They are not shapes declarative and do not introduce a new name: they update a link that must already exist. In return they evaluate the left side only once, a detail that with a simple name is not noticed but which counts when the target is a list element (xs[i] += 1, chap. 9): so the index is not calculated twice.

Read the example distinguishing the name from the value: after x = 42, x is a bond of the current environment; y = x + 8 reads that binding and stores the result 50 in a binding different; x = x + 1 first calculates 43 and then replaces the value associated with x. As a result y remains 50: it is not an automatic alias of the expression that produced it. The assignment returns the new value, so it can appear inside an expression, but that doesn't mean that each assignment is global: function, lambda and let define distinct scope rules.

Finally, renaming is not the same as mutating an object. With x = 43 the bond of changes x; with xs[1] = 43 changes an element of the list to which xs refers. If a middle name points to the same list, it will see the mutation; a local reassignment of xs, however, does not change automatically the link of the other name. This difference becomes essential when one function shares a list with the caller.

4. Operators and precedence

The parser is a Pratt with twelve levels. «Pratt» means that each operator has a number of precedence and the parser, reading from the left, knows when to stop and return control to the lowest level: it is a compact way of describing the tree without writing a rule for each combination of operators. From lowest to highest precedence:

level operators associativity
1 = += -= *= right
2 x -> e, (a, b) -> e, c ? a : b right
3 || left, short circuit
4 && left, short circuit
5 == != < <= > >= in isa is left
6 a:b range, no spaces
7 + - left
8 * / % left
9 -x !x +x $x prefixes
10 ^ right
11 e::T assertion of type
12 f(args) xs[i] a.field postfixes, with no space before ( and [

Levels 6, 8 (division), 9 ($x), 11 (::), and some comparison operators exist only in Triad-Full. In Triad-Core the levels actually used are ten, because the range is missing division, $x, :: and the operators in, isa, is; once those are removed, the table becomes compact but the relationship between the operators who remain is the same. The number twelve, which the glossary reports, is therefore the Full profile count: is not in contradiction with the ten levels of Core, it is the account for a larger profile. [Core]

Precedence decides how the parser groups the operators, not what computation occurs for first in every possible program. For example, 2 + 3 * 4 is read as 2 + (3 * 4): the multiplication belongs to a stronger level than addition. The parentheses do not change the rule of language; they make a programmer's choice explicit and help the reader. Associativity instead solves the parity of precedence: 2 ^ 3 ^ 2 is 2 ^ (3 ^ 2), while the chain subtractions cluster on the left. When the precedence is unfamiliar, write the brackets is a form of executable documentation.

Grouping should not be confused with evaluation. && and || are short-circuit operators: the second operand is evaluated only if the first does not already determine the result. This allows to put a control on the right that depends on a valid value on the left, for example before verify that an index is within bounds and then read the list. In Core every condition must still produce a Bool; an integer or a list are not implicitly converted to true/false.

4.1 Integer arithmetic

Core's arithmetic is entirely integer and these four rules should be read as a single model, not as isolated curiosities: the Int type is a 64-bit block, operations treat it as such, and the division is left at Full because it requires another type of number.

  • + - * ^ to Int with 64-bit wrap (two's complement);
  • % is the signed remainder of the dividend, like Julia's rem: -7 % 3 == -1;
  • ^ with negative exponent is an error; % for zero is an error;
  • / does not exist in Core: the division is Triad-Full.
println(2 + 3 * 4, " ", (2 + 3) * 4, " ", 2 ^ 3 ^ 2)
println(7 % 3, " ", -7 % 3, " ", 10 % 4)
println(9223372036854775807 + 1)

Output:

14 20 512
1 -1 2
-9223372036854775808

Note 2^3^2 == 512: the exponent is right associative, as in mathematics.

The wrap is not a flaw to work around: Int is a 64-bit integer and the arithmetic is that of two's complement, so exceeding the maximum brings you back to the minimum. If your calculation can grow beyond 64 bits, in Full you can switch to Float (with its precision limits); in Core you must design the calculation to stay within bounds, for example by checking values before multiply.

% follows the dividend sign because it is the remainder of integer division truncated towards zero, not the mathematical form, which would always be non-negative: -7 % 3 is -1 and not 2. The distinction counts in algorithms that use the remainder to alternate indices or to normalize negative values.

Finally /: in Core it does not exist because the exact division of two integers does not have a type to live in without the floating point numbers. In Full / produces a Float and div does integer division; if you work in Core, the entire division is written by hand, as in the example in chapter 11.4.

5. Flow control

In Triad everything is an expression: if, while, let, begin have a value, that of the last executed statement (nothing if there is none).

The exceptions are return, break and continue: they don't produce a value, they stop the flow. Assignment, on the other hand, is an expression (chap. 3), and this uniformity is what makes it possible write v = if condition … end without special syntax: a block is an expression like lo it is a sum.

This rule unifies two uses that often have separate syntaxes in other languages: choose a branch and calculate a result. In v = if condition ... end, the complete expression produces the value of the last expression of the chosen branch; the code of the unchosen branches is not executed. Instructions that produce output or mutate a list can fit in the same block as an expression that evaluates to a value: the result of the block is the last expression, not one automatic combination of all intermediate results.

The conditions are intentionally restrictive: if, while, ternary, && and || ask a Bool value. You do not use an "implicit truth" rule that interprets 0, empty strings, or lists empty like fakes. This makes type errors visible close to the decision that has them provoked, instead of transforming them into unexpected branches.

5.1 if / elseif / else [Core]

function rank(x)
    if x < 0
        "negative"
    elseif x == 0
        "zero"
    else
        "positive"
    end
end
println(rank(-3), " ", rank(0), " ", rank(7))
v = if 2 > 1 :yes else :no end
println(v)

Output:

yes

In the example classify returns the last expression of the chosen branch, so it is not needed no return. v = if 2 > 1 :yes else :no end shows the same thing without function: the block is a value and v receives :si. The branch that doesn't win isn't executed at all, it isn't evaluated and then discarded: if it contained a print or mutation, you wouldn't see it. The ternary c ? a : b is the short form of if and has the same precedence as ->. [Core]

5.2 while, break, continue [Core]

break and continue act on the innermost loop.

    i += 1

The first loop adds only the odd ones: continue skips the rest of the body, so the addition doesn't happens for evens, and the i counter has already been incremented before the jump. If the increase had it been at the bottom of the body, continue would have skipped it and the loop would have been infinite: It's the classic continue trap in manual counter loops, and why it's convenient increase immediately, before any possible early exit.

break and continue act on the innermost loop; there is no etiquette for dating two loops in one go, so in that case you use a state variable.

In Core there is no for: you iterate with a counter and while. In Full for exists (ch. 5.6).

5.3 let and begin [Core]

let introduces a new scope with local bindings. begin … end groups statements into one expression, but it is not "without consequences" on the scope: the reference interpreter updates a name already bound outside the block, while a new name assigned inside begin is not visible out. The specification does not list begin among the constructs that introduce environments and no cases of conformity sets the point: for new names it is prudent to treat the block as a boundary.

x = 1

    let x = 20
        println(x)
    end
    println(x)
end
println(x)

    a = 2
    at * 21
end

Output:

10
1
42

The example shows three distinct bindings for x: the external one, the one introduced by the first let and the one introduced by the second. Each let creates a new environment, and a name is looked up first in the innermost environment; for this reason the three prints give 20, 10, 1 and none of the three bindings touches the others. begin, however, is just a grouping: the example assigns a = 2 e uses a * 21 in the same block, so it doesn't depend on what remains visible after. The rule from keep in mind is that the block is not used to release new names: if a value must be used out, assign it to a name that already exists before begin or return it as a value of the expression. In practice let is used when you want to isolate a name or reuse an already taken name without altering the external bond; begin is used to group statements into a single expression.

5.5 Comprehensions [Full]

[9, 16]

The comprehension is sugar for a loop that accumulates into a list: for each x of 1:4 evaluates x^2 and adds the result, without an explicit counter. In Core [e for x in xs] does not exist and the handwritten functions in the chapter do the same job 22.1; in Full, comprehension is often the most readable form, as long as the expression remains short.

5.6 try / catch [Full]

In Full the error is a value, so try has two forms: with catch the managed branch produces the expression value; without catch, the error becomes the value of the expression.

e = try div(1, 0) end
println(iserr(e), " ", e.kind)

r = try div(1, 0) catch err; 0 end
println(r)

Output (golden Full):

true domain
0

The two forms are not interchangeable. try and end doesn't handle the error: it makes it the value of the expression, so you can check it with iserr and decide later. try and catch err; h end instead retrieve: bind err to the error and evaluate h, whose value becomes the result. In the first case e is an Err, in the second r is 0. Choosing between the two is a design decision: the first form keeps the error in the normal flow, the second confines it to a precise point. It's the reason why to which Chapter 11 insists that “error as given” does not mean “the program continues from only": without a try to observe it, the error reaches the upper level and the program terminates.

6. Functions

6.1 Three forms of definition [Core]

A named function is defined in two ways — short form and block form — and the third form is an anonymous function tied to a name. The difference is only syntactic: the function you get is the itself. The short form is used when the body is a single expression; the form function … end when the body has multiple statements or a return that exits before the end; the lambda assigned to a name is useful when the function value arises inside an expression.

# short form: the body is an expression
square(x) = x * x

# block form: the value is that of the last expression
function compute(n)
    m = n + 1
    m * 2
end

# anonymous function assigned a name
multiply = function (a, b)
    a * b
end

println(square(4), " ", calculate(3), " ", multiply(6, 7))

Output:

16 8 42

square and calculate are named functions, multiply is a function-type value bound to a name: from the point of view of the call there is no difference. Choose the shape that makes it most readable the body, not the one that seems most modern; the short form with only one expression makes it obvious that there are no hidden effects between the lines.

6.2 return, recursion, arity

return e exits the function immediately; return alone returns nothing. A named function it's visible in your body, so direct recursion works. The number of arguments must coincide with the parameters. [Core]

function size(n)
    if n > 100
        return :large
    end
    :small
end
factorial(n) = n < 2 ? 1 : n * factorial(n - 1)
fib(n) = n < 2 ? n : fib(n - 1) + fib(n - 2)
gcd(a, b) = b == 0 ? a : gcd(b, a % b)
println(size(500), " ", size(5))
println(factorial(10), " ", fib(15), " ", gcd(48, 18))

Output:

big small
3628800 610 6

A call can be read as a precise sequence: the arguments are evaluated, the context of the function, you associate the values with the parameters and execute the body. The body ends in one of two ways: reaches the end and returns the last expression, or executes return, which immediately interrupts the body and returns the indicated value. return without expression returns nothing. A recursion is a new call with its own set of local parameters; the base case prevents you from continuing to create endless calls.

Arity is also part of the signature in Core: sum(1, 2) is not interchangeable with sum(1). Triad-Full adds types to signatures and allows multiple methods with the same name; this doesn't change the notion of calling, but adds a method selection step before executing the body.

One last practical note: deep recursion consumes call space, so per depth large, a while with an explicit state is better (chap. 22.6). The base case is not a formality: without it the recursive call doesn't stop and the program doesn't arrive at a result.

6.3 Higher-order functions

Functions are first-class values: they pass, they return, they compose. In Core map, filter and reduce do not exist: they are written by hand (chap. 22.1). In Full they are builtins. [Core]

function apply_all(f, xs)
    out = []
    i = 1
    while i <= length(xs)
        push!(out, f(xs[i]))
        i += 1
    end
    out
end

Output:

[1, 4, 9]

In Full, reduce(+, xs) and map(sq, xs) work because the operators are also functions.

The point of apply_all isn't function specific: it's that f is a parameter like the others, and x -> x * x is a value constructed at call time. This is the difference between writing ten almost equal cycles and write a cycle only once; in Core map and filter do not exist because the bootstrap language needs to stay small, not because the idea is foreign to Triad. Le functions of chapter 22.1 are the practical answer: write them once and use them again.

The annotation is not decorative. In Triad-Full a function declares the capabilities it uses, and the runtime checks that the caller allows them (chap. 15); in Core the control does not exist, but writing !io now means not having to rewrite the signature when the program switches to Full. The word I is a permission, not a descriptive label: it says what the function can produce output, and the caller must be authorized to do so.

7. Types and multiple dispatches

A generic function is a collection of methods. Redefine the same signature overrides the method previous. Among the applicable methods (same arity, each argument subtype of the parameter) wins the most specific. [Full]

area(n::Number) = :number
area(n::Int) = :int

println(area(1))
println(area(1.5))

Output (golden Full):

int
number

The example should be read as a search: area(1) has an Int, which is a subtype of both Int and Number; both methods are applicable, but Int is more specific and wins. area(1.5) has a Float, which is a subtype of Number but not of Int, so there is only one applicable method left. If had I only defined area(n::Number), both calls would have used that: dispatch does not chooses the "best" method, chooses the most specific among those that accept the arguments. A method A is more specific than B if each of its parameters is a subtype of the corresponding parameter of B and the signatures differ.

  • If no method is applicable: Err(:method).
  • If multiple methods are maximal: Err(:ambiguous).
  • If the name is also a builtin (for example + on numbers), the builtin is used.

Dispatch can be modeled as a two-step search. First we eliminate the methods with incorrect arity or with at least one argument that does not satisfy the declared type; then they compare those remaining according to the subtype relationship, parameter by parameter. One method is more specific only if it is no longer general in any position and is general in at least one. So it's not enough choose the most recently added method. If two incomparable signatures remain, the call is ambiguous and produces Err(:ambiguous) instead of depending on the order of the files or the order of registration. This behavior allows you to add specialized methods without rewriting the generic function, while keeping explicit the cases that do not have a univocal answer.

Operators are extended as functions, redefining them:

struct Point
    x::Float
    y::Float
end

function +(a::Point, b::Point)
    Point(a.x + b.x, a.y + b.y)
end

p = Point(1, 2) + Point(3, 4)
println(p.x, " ", p.y)

Output (golden Full):

4.0 6.0

8. Lambdas, closures and scopes

8.1 Lambda [Core]

A lambda is an unnamed function: x -> x * 2 is a value, not a definition. The shape (a, b) -> … declares multiple parameters, and the body is an expression or a block. Lambdas yes pass as arguments and return as results, and that's how an order function above (chap. 6.3) describes an operation without carrying it out immediately.

double = x -> x * 2
sum = (a, b) -> a + b
apply = f -> f(3)
println(double(5), " ", sum(1, 2), " ", apply(x -> x * x))

Output:

10 3 9

A lambda with a multi-statement body is written with begin … end or with function (…) … end. Le parameterless lambdas (() -> …) are not supported: use function () … end.

8.2 Closures

A lambda captures the environment in which it is created. According to SPEC-CORE §5 the captured variables are shared: mutations are visible. [Core]

function add(n)
    x -> x + n
end
f = add(10)
g = add(100)
println(f(5), " ", g(5))

function counter()
    v = 0
    x -> begin
        v += x
        v
    end
end
acc = counter()
acc(5)
println(acc(10))

Output:

15 105
15

Caution. The Windows seed captures by value and covers only the last binding of the frame: a accumulator as counter may not work on seed. The JS interpreter and specification use the shared model.

A closure doesn't keep a snapshot of just the text of the lambda: it keeps access to the bindings that his body can read. In the first example the function returned by add(10) maintains the value n = 10 even after the call to add has finished; add(100) creates a closure distinct. In the counter, however, the variable v is a shared link: each call updates the same state and the next one observes it. It's why a closure can represent a small object with private status. It is also the reason why the specific behavior of the seed Windows should be verified separately from the reference interpreter.

The difference between shared capture and value capture is not theoretical: with the shared model two closures created from the same frame see the same state, with the pattern for value each has his copy. When you design a stateful object, know which model you're using, because that's it which decides whether two counters are independent or not.

8.3 The rules of scope

The rules follow a single principle: the scope is lexical, i.e. it matters where the code is written, not where it is called from. From that principle derive the five rules that follow; read them in order helps predict what actually changes an assignment.

  1. function, lambda, let, while, for and comprehensions introduce environments; a name is visible in the environment in which it is linked and in the internal ones (lexical scope), never in those external.
  2. Within a named function the assignment binds in the local frame: a function not edit globals.
  3. Inside a lambda assigning to a name already bound outside updates that binding.
  4. At top level loops can update globals.
  5. let x = … creates a new x: assigning x inside the let does not affect the outer x.
x = 1
function f()
    x = 2
    x
end
println(f(), " ", x)
c = 0
function increment()
    c += 1
end
increment()
println(c)

Output:

2 1
0

To get a result out of a function, return it — or use a list, which is mutable.

The example shows the most important case: f returns 2 and the global x remains 1, because assignment within a named function creates a local binding. increment increments a local binding c that is born and dies in the call, and the global c remains 0. It's not an oversight language: it is what makes the behavior of a function independent of the global state. When you need shared state, there are two ways — a mutable list passed as topic (chap. 9) or a closure (chap. 8.2) — and in both cases the sharing is visible in the signature or definition.

9. Lists

A list is heterogeneous, nestable and mutable. The indices start from 1. [Core] A list is written in square brackets, [1, 2, 3]; the order of the elements is significant and i values can be of different types. Mutability is the property that distinguishes the list from a record: the list grows and changes, and multiple names can observe the same list. It's the structure supports almost all Core code, from records to queues, from environments to parsers.

xs = [1, 2, 3]

push!(xs, 4)
xs[1] += 100
println(xs)
alias = xs
push!(aka, 5)
println(xs)

Output:

1 3
[101, 2, 3, 4]
[101, 2, 3, 4, 5]

push! mutates the list and returns it. The lists are references: two names can indicate the same list, as seen above.

The fact that push! returns the list, and not nothing, is a convenient choice: it allows you to chain the addition with another operation, but it also makes it possible to write xs = push!(xs, 4), which is redundant but harmless. Assignment to an element (xs[1] += 100) also works with compound operators: the left side is evaluated only once, so the index is not calculated twice.

A list is a mutable object; a variable contains a reference to that object. If ys = xs, the two names allow you to reach the same list: push!(ys, value) and xs[i] = value are also observable by reading xs. If you instead write ys = [1, 2], you have replaced only the bond ys; xs continues to refer to the previous list. This distinction explains why assigning a list does not automatically create a copy of it and because list arguments can be used to share state between functions.

The 1-based convention is consistent with examples and specifies: to visit n elements, the counter starts from 1 and the typical condition is i <= length(xs). In one loop, update the counter after reading the item avoid skipping the first item; increase it in each iteration ensures that the condition will sooner or later become false. On the Windows seed the auxiliary function experimental get(xs, i) is different and 0-based: it should not be used as if it were the standard semantics of the lists.

The choice to start from 1 is not an aesthetic detail: it makes access consistent with the positions human and range-based, and allows length(xs) to be used as the last valid index. The price is that a index calculated with 0 in mind must be corrected; the typical error is xs[0], which does not return a value but produces an error. An out-of-range index is nothing: in Core the program ends, in Full comes an Err(:bounds) to handle. For this reason, when the index is calculated, it is good practice to check it first with 1 <= i && i <= length(xs).

The sum of the elements with an explicit loop:

i = 1

    tot += xs[i]
    i += 1
end
println(tot)

Output:

115

The loop shows the canonical form of traversal in Core: counter from 1, condition i <= length(xs), reading xs[i]. length is recalculated every iteration, so if the loop body changes list border moves; mutating the list as you traverse it is possible, but it must be done with awareness. Adding elements lengthens the list and loops through them will visit; in Full, where pop! and append! exist, removing items as the index grows does skip the next ones. In Full there are also reverse, sort, sum, first, last, rest, pop!, append!, vcat, collect and the x in xs operator. None of these names exist in Core: if you need them, write them to hand with while and push!, as in chapter 22.1. It's not a loss: handwritten algorithms they show what they do and how much they cost, and in a bootstrap this transparency is worth more than brevity.

11. Errors as data

This is one of the main ideas of Triad: error is a value, not an exception interrupts the program.

11.1 The Err form

An error is an Err value with three fields:

  • kind::Symbol — the category, on which dispatch can be done;
  • msg::String — the message;

The three fields separate three different questions: what happened (kind), how to tell it (msg) and what information is needed to react (data). 12. Contracts

A contract is a precondition (requires) or a postcondition (ensures) declared in the body of a function. [Full]

A contract is not a comment: it is an executed condition, and a violation of it is a mistake as given. It serves to make explicit what a function expects from those who call it and what it promises to those who receive it, without entrusting the pact to the good will of those who read it. It does not demonstrate that the property holds for every possible input — it controls it for the executions that occur — but turns a silent violation into an Err reporting which clause failed.

function safe_div(a::Number, b::Number)::Float
    requires b != 0
    ensures abs(result * b - a) < 1e-9
    a/b
end
  • requires c is checked where it appears: by convention at the beginning of the body.
  • ensures c is recorded and checked at function exit, with result bound to return value, after checking the return type.
  • A violation produces Err(:contract, "requires violated in safe_div: b != 0", Info(fn, clause, cond[, result])). cond contains the code of the condition: it is data, it can be inspected.
  • The conditions are pure: an effect inside a contract gives Err(:effect).
  • At the top level requires c works like an assertion.
  • ensures only makes sense inside a function: use result, which exists only when the function is going to return a value. Outside a function there is no result to refer to.
println(safe_div(6, 3))

e = try safe_div(1, 0) end
println(e.kind)
println(e.data.clause)
println(e.data.fn)

Output (golden Full):

contract

safe_div

In the example safe_div(6, 3) produces 2.0: the Float return type converts the result and exposes it as a promise kept. safe_div(1, 0) never gets to divide: the precondition comes checked at the beginning, the error is already a value and the program continues. The error message carries with it clause = requires and fn = safe_div, so the caller can distinguish a violation of entry from a promise of exit not kept without reading the text.

The checking sequence is significant: the body evaluates the clauses in the order in which appear; preconditions are checked at the point where they are declared, while the postconditions are preserved until the function completes. The final value comes first subjected to the return constraint and then exposed as a result to the ensures clauses. A contract error includes which clause failed and the code that represents it, so who calls can distinguish an entry violation from a broken exit promise. I contracts control an observable invariant, but do not mathematically prove that it holds for every possible input: they are evaluated for the executions that occur.

13. Budget

A budget limits how many steps the program can consume. A step is a call, an iteration of loop or a resolution step. When the budget runs out, the value of the with is Err(:budget): The program does not crash or terminate. [Full]

r = with budget(steps = 10_000)
    while true end
end
println(r.kind)

Output (golden Full):

budget

Budgets nest and the tightest applies. A with converts only the exhaustion of to a value own budget, while that of an external budget continues to propagate. solve … steps N is the query-specific budget.

Budget measures work, not time: two runs of the same program with the same budgets consume the same steps, so the result is reproducible. A timeout based on the watch it would not be and would make the tests unstable. This is why the limit is part of the language and not the environment: a program can decide what to do when it runs out, e.g that decision is also code.

The logic engine uses an explicit stack: infinite recursion, even left, ends in Err(:budget) is not in a stack overflow.

The limit is part of the calculation result because the program can choose how to treat it: show a diagnosis, reduce the problem or return a partial result only if your logic allows it. Don't confuse limit n, which limits the number of solutions returned, depth d, which cuts branches beyond a depth, and steps s, which limits the overall work. A query that has explored the intended space without finding solutions returns an empty list; a query stopped by exhaustion of steps instead reports Err(:budget).

14. Tracks

The trace of a calculation is a value, not printed output. [Full]

    fib(3)
end

Output (golden Full):

fib(3) makes 5 calls (fib(3), fib(2), fib(1), fib(0), fib(1)): trace records two events for each call, :call and :exit, so 10 events. For fib(5) that's 15 calls and 30 events — is the value expected from the garanzie_core conformance case.

with trace … end returns Traced(result, trace) with the :call and :exit events of each generic function called in the body. solve … trace returns Traced(result, trace) where result is the list of solutions and events are the gates of the Byrd box model (call, exit, redo, fail) plus depth, when a branch is cut by depth.

Events are records: they are filtered and counted like any other value.

Collecting a trace is not free: each event is an allocated value, and on large calculations the trace can weigh more than the result. Ask it when you need it, not by default.

A trace adds a time dimension to debug data: two runs can have it same result but follow different paths, for example if a query had to try and discard alternatives. Instead of writing logs inside each function, the caller encloses the calculation in with trace or ask trace to solve; the result and events come returned together. This keeps the application result and diagnostics separate, and allows to analyze the trace with the same tools used for lists and records.

Glossary of trace events (Byrd gates)

When using solve … trace, each search step produces an event that logs at what reference (which goal, which clause, which logical variables) is being worked on. Four o'clock Byrd box model doors are:

door when it occurs meaning
:call you enter a goal start of candidate clause evaluation
:exit unification successful the goal is demonstrated: it is the "success" of the research
:redo backtracking we go back to look for another solution
:fail no applicable clause the goal fails: no solution for that branch

Important Notes:

  • "success" and "fail" are not generic outcomes: they are the :exit and :fail ports of the trace, refer to the current goal/clause. The failure of a goal is not an exception: it occurs as empty solution list in the result of Traced(result, trace).
  • depth appears as an additional event when a branch is cut from the depth limit (solve … depth N), signaling that the search was aborted before an :exit/:fail.
  • Events are ordinary records: they are filtered ([e for e in t.trace if e.port == :fail]), they are counted (length), they are inspected (e.args, e.depth) like any other Triad value.
  • The reference of each event is the current goal and the logical variables (?x, ?y, …) involved in that passage: by reading the trace one reconstructs which alternative it was tried and why it failed.

15. Declared effects

The functions are pure by default. The effects are declared in the signature, after i parameters. [Full]

“Pure by default” is a security choice: if you forget a statement, the function cannot do more than expected, and the error comes when the effect is attempted. In this sense an effect is a capability, not a descriptive annotation: !io says that the function has the permission to print, and the dynamic check checks permission at run time.

function hello(name::String) !io
    println("hello, ", name)
end

function learn(x) !state
    fact seen($x)
end
effect operations
I println, print
state fact/rule executed inside a function (modifies the knowledge base)

The control is dynamic. A function executes only with the effects it declares, and only if the caller allows them. If a pure function calls println, or calls an !io function, yes get Err(:effect); data contains fn, caller and missing.

Purity by default means that a function can calculate and return values without changing the external state or producing I/O; it doesn't mean the runtime parses statically every possible path before execution. Dynamic control observes the effects while occur and compares them with the active context. Local mutations and list mutations are not classified as effects declared in this specification: !state refers to the modification of the knowledge base via fact and rule, not to any assignment.

  • The top level allows all effects.
  • Lambdas inherit the effects of the context in which they are executed.
  • Macros and contracts are pure.
  • Reading the knowledge base (solve, calling a predicate) is pure.
  • Local data mutation (push! on a list, assignment to local variables) is not a effect: only changes values reachable from the local environment.
noisy function()
    println("I make noise")
end

    noisy()
end

noisy does not declare !io, so its println is a disallowed effect; quiet there calls from a pure context and gets the same error. data contains fn (who tried the effect), caller (from where) and missing (which effect was missing): these are the three pieces of information They are used to correct the signature. The control is dynamic, so a branch that doesn't execute doesn't produces effect errors, and there is no static analysis that warns you first: the statement is a as long as the runtime checks as the code runs.

16. Logic

Triad integrates logic programming into block syntax: the facts and the rules are top-level constructs, not an embedded language. [Full]

Facts and rules form the knowledge base, which the program builds as it runs. A fact asserts that a relationship is valid; a rule says that it is valid provided that other things are valid. solve asks a question at the base and returns the answers as values: there is no interpreter separate to invoke, because the logic is within the same syntax and the same engine as the rest of language.

16.1 Facts, Rules, Terms

fact parent(:tom, :bob)
fact parent(:bob, :jim)

rule ancestor(?a, ?d) :- parent(?a, ?d)
rule ancestor(?a, ?d) :- parent(?a, ?x), ancestor(?x, ?d)

Within a term:

  • :atom is a symbol; ?x is a logical variable; numbers, strings and lists are themselves;
  • f(t1, t2) is a composite term. ?x + 1 is also a term (+(?x, 1)) and is not rated;
  • a bare name is a value from the current environment, read at the time fact is executed, rule or solve: chi = :bob; solve parent(chi, ?c);
  • $(expr) explicitly inserts a calculated value: fact age(:bob, $(2026 - 1975));
  • [a, b] and [?h | ?t] are lists and forms that unify with lists;
  • the name of a struct with arguments, such as Point(?x, ?y), unifies with instances of that struct.

Variables in a clause are renamed with each use (standardization aside). Unification does the occurs-check: solve ?x = f(?x) has no solutions.

To read a query you need to distinguish terms from normal calculated values. A symbol as :alice is a constant term; ?who is a logical variable that searches for a value; a shape like parent(:alice, ?who) describes a goal to be proved. Logical variables are not variables local Triads assigned with =: the engine searches for associations that make the goal compatible with facts and rules. In particular, ?x + 1 within a term does not compute itself; the is operator explicitly expresses the request to evaluate an expression using already bound variables.

Unification progressively builds a set of associations. If they compare parent(:alice, ?who) and parent(:alice, :bob), the corresponding arguments are the same and the engine can bind ?who to :bob; if an argument is different, that attempt fails. When more clauses can satisfy a goal, backtracking back to the choice point and testing the clause next. Each solution is a snapshot of the variables required by the query; a list empty means "no proof found", not an execution error. The limit limits, depth and steps control how many solutions or search steps are allowed.

16.2 The goals

A goal is the description of what you want to be true: the engine looks for bonds for the variables that they make it demonstrable. The table collects the forms that a goal can take; the first two are the most important ones, because p(t…) is the only way to query the knowledge base and the conjunction it's the only way to ask for more things at once.

g1 && g2, (g1, g2) conjunction; in rules also with ,
g1 || g2 disjunction
!g, not(g) denial for failure
not(b) out of a goal is a function: negate a Bool (not(true) == false)

16.3 solve is a value

solve returns a list of Solution. It doesn't print anything: it's a value like any other.

fact parent(:alice, :carol)

Output (golden Full):

[{who = :dave}]

1

Each solution binds the non-anonymous query variables, in the order they appear. Le variables left free remain ?x#n. vars(sol) returns bound names. Solution is a record with the query names: sols[1].who reads the binding, and vars(sol) lists the names. The result of solve is a normal list, so you can filter, sort or count the solutions with the tools of the rest of the language: the logic does not produce a special format, produces values.

solve options:

  • limit n — at most n solutions;
  • depth d — branches deeper than d are cut (fail);
  • steps s — at most s resolution steps, otherwise Err(:budget); the default value is 1 000 000;
  • trace — see chap. 14.

The options are not equivalent: limit stop the search when you have enough solutions, depth cuts branches that are too deep and considers them failed, steps limits the overall work and reports exhaustion with Err(:budget). Distinguishing them matters because only the last one is a mistake: the other two produce a partial but legitimate result.

16.4 A predicate used as a function

Calling a predicate where a value is expected returns a Bool: tells if the goal is demonstrable.

    println("alice is dave's grandmother")
end

Prolog style append:

Denial for failure:

Output (golden Full):

[:bob]

!parent(p, ?_) is negation by failure: p passes the filter only if the goal parent(p, ?_) it is not demonstrable. :tom has a child, so it doesn't pass; :bob has none, so it passes. The anonymous variable ?_ is the one that does not appear in the result: each occurrence is a variable new, so you don't have to invent a name for a variable you don't care about.

17. Code as given

The parser produces only one node type, Node(head, args). It is the same tree as the kernel executes, which :( … ) returns as a value and which triad --tree prints as an S-expression. [Full]

17.1 Odds, unquotes, eval

(call + (dot a x) (call f b 2))
49

Inside a quote, $x and $(e) insert the value of an expression: if it is code it is nested, if it is a number or a list it becomes a constant, if it is a Symbol it becomes an identifier. eval(c) executes code in global scope. The other builtins in the "code" group are parse, unparse, sexpr, Expr and gensym.

Quoting and evaluating are opposite but not interchangeable operations. The parser normally transforms the source in a tree and the evaluator executes that tree; :(...) stops the process al boundary between the two phases and returns the tree as an Expr value. eval(expr) delivers it by new to the evaluator, in global scope. The unquote $x inside a quote inserts the value calculated of x in the new tree: if it is an Expr, insert code; if it is a number, create a node constant. sexpr is for inspecting the structure and does not run the program.

The example shows the complete journey: :(a.x + f(b, 2)) returns an Expr without executing it, c.head is call and sexpr writes it in linear form. :($n * $n) with n = 7 does not create a function: create a tree that already contains the constant 7, and eval executes it. The difference between eval and a normal call is the scope: eval starts from the global scope, so it doesn't see the local variables of the person invoking it. This is why eval is used to build complete code, not to read context values.

18. Macros

A macro takes arguments as code, not evaluated, and returns code, which is then executed in place of the @name(...) call in the caller's scope. [Full]

The difference compared to a function is not only technical: a function receives already calculated values, therefore he cannot decide whether to evaluate a topic once, twice or never. A macro receives the source form, and this is its only real reason for being: it is used when behavior depends on the code, not on the value of the arguments.

macro unless(c, body)
    :(if !$c; $body; end)
end

macro swap(a, b)
    t = gensym(:tmp)
    odds
        $t = $a
        $a = $b
        $b = $t
    end
end

x = 1
y = 2
@swap(x, y)
println(x, " ", y)

Output (golden Full):

2 1

The expansion is pure (§15) and unhygienic: gensym() is used for temporary names.

This distinction is important for the effects. A function normally receives values already calculated; a macro receives the source shape and can then decide whether to insert it once, multiple times times or not insert it. Triad macros are unhygienic: a temporary name introduced by macro can collide with a caller name. gensym creates a cool symbol for temps, but it does not automatically make every free reference safe. For this reason it is advisable to limit the macro to small transformations and inspect the expanded tree before attributing to the result unexpected behavior.

18.1 Code generating code

function poly(coeffs)
    acc = :(0)
    i = 0
    for c in coeffs
        acc = :($acc + $c * x ^ $i)
        i += 1
    end
    acc
end

p = poly([1, 2, 3])
x = 2
println(eval(p))

Output (golden Full):

17

poly builds a tree on each spin: :(0) is the starting point, and each coefficient grafts the previous tree with $acc, the constant $c and the exponent $i. The for here works on values normal; only quote and unquote build code. With [1, 2, 3] the final tree represents 1 + 2 * x + 3 * x^2, and with x = 2 the value is 1 + 4 + 12 = 17. eval(p) searches for x in scope global: if x had been local to a function, the tree would not have seen it.

20. Command line and REPL

A Triad program doesn't just live inside a file: the standard also defines how it is invoked the interpreter. The triad interface is normative (SPEC §14), that is, it is part of the language how much the syntax; if two implementations read the arguments differently, the programs do not they are portable.

triad # REPL
triad FILE [ARG...] # execute FILE; ARGS == [ARG...]
triad -l FILE # loads FILE and opens the REPL
triad -i FILE # execute FILE and then open the REPL
triad -e CODE # execute CODE
triad -E CODE # execute CODE and print the value
triad --tree FILE # print uniform tree as S-expression
triad -q # REPL without banner
triad -h, --help
triad -v, --version
triad - # read script from stdin

The options cover three different needs. -e and -E are used to test a fragment from the terminal, with the difference that the second also prints the value; -l and -i combine a file and session interactive, depending on whether the file is loaded or executed; --tree shows the uniform tree from Chapter 17, useful when you want to see how the parser has grouped the code. The final dash reads script from stdin, so Triad can fit in a pipeline.

  • The .triad/.td extension can be omitted; the shebang #! is ignored.
  • The program sees the arguments in ARGS, list of strings, without the program name.
  • Exit codes: 0 success, 1 unhandled error (to stderr), 2 invalid use.

This interface is normative, but not all implementations cover it: Windows seed today executes a file and that's it, without REPL or options (chap. 29). To run the examples in this manual just the form triad FILE, or the node seed/dev/triad_core.cjs shown at the beginning.

20.1 The REPL

The REPL is an interactive session: you write an expression, see the value, and the definitions remain active between one command and another. It is useful for exploration, for proving a logical goal or for understanding because an expression gives a certain result, without creating a file every time.

The REPL is Prolog style:

triad > 1 + 2
3
triad> ?- ancestor(:tom, ?d)
?d = :bob ;
?d = :liz.
triad> parent(:jim, ?x)
false.

The answers show the two modes of the REPL: 1 + 2 is a normal Triad expression and prints the value; ?- ancestor(...) is a query and prints the solutions one by one, with ; to ask for the next one and . to stop. false. is not an error: it means there is no other solution.

  • Blocks remain open until closed by end.
  • ?- goal (the trailing . is optional) executes a query with the solve options: limit, depth, steps, trace.
  • A statement that is a goal on a knowledge base predicate is treated as a query.
  • After each solution: ;, n or space for the next one, a for all the remaining ones, enter or . to stop. false. means no other solution.
  • Commands: :load FILE… (:l), :reload (:r), :listing [name] (:ls), :tree CODE, :reset, :help (:h), :quit (:q, halt, Ctrl-D).
  • Ctrl-C stops the calculation in progress; an unhandled error is printed and the REPL continues.

21. Bootstrap primitives

Five primitives are used by S1 to read and analyze the Triad source. They are not part of Triad-Full (SPEC-CORE §8): Use them only in bootstrap code.

They are primitives and not functions because they are under the language: they are used by a written interpreter in Triad to read your source as a sequence of bytes. This is why they are not part of Triad-Full: An application program should not depend on them, and the code that uses them is not portable outside the bootstrap. Their presence in the Core profile explains why a string is one sequence of bytes and not a sequence of characters (chap. 10).

The first loop counts the digits by comparing the byte to 48 and 57, which are the ASCII codes of 0 and 9: This is how a lexical analyzer distinguishes a number from a name without having functions on strings (chap. 23, exercise 6). 22. Style and idiomatic patterns

This chapter does not introduce new constructs: it shows how to combine those from previous chapters in cases that always occur — transform a list, represent a record, hold a state shared, construct a string. They are patterns, not rules of language, and you will recognize them in the project code.

22.1 Higher-order functions written in Core

In Core there are no map/filter/reduce: they are written once, with while and lambda, and then they use everywhere.

The difference compared to the Full versions is not only in the name: here the loop is explicit, so you see the index, the end condition, and the point at which the item is added. If one day one of these functions gives an unexpected result, the defect is visible in three lines.

function map(f, xs)
    out = []
    i = 1
    while i <= length(xs)
        push!(out, f(xs[i]))
        i += 1
    end
    out
end

function filter(p, xs)
    out = []
    i = 1
    while i <= length(xs)
        if p(xs[i])
            push!(out, xs[i])
        end
        i += 1
    end
    out
end

function reduce(f, acc, xs)
    i = 1
    while i <= length(xs)
        acc = f(acc, xs[i])
        i += 1
    end
    acc
end

xs = [1, 2, 3, 4, 5, 6]
println(map(x -> x * x, xs))
println(filter(x -> x % 2 == 0, xs))
println(reduce((a, b) -> a + b, 0, xs))

Output:

[1, 4, 9, 16, 25, 36]
[2, 4, 6]
21

map and filter return new lists, reduce returns a value; in all three cases the received function is a normal parameter, so the behavior can be changed without touching the cycle. Note that reduce accumulates in acc and does not mutate xs: the input list remains the same.

22.2 Records as tagged lists

In Core there is no struct: a record is a list with a symbol as a tag in the first position. The convention is important because without struct there is no nominal type: the meaning of the record it lies entirely in the tag and field order, which the program must respect itself.

point(x, y) = [:Point, x, y]
px(p) = p[2]
py(p) = p[3]
sum_points(a, b) = point(px(a) + px(b), py(a) + py(b))
p = sum_points(point(1, 2), point(10, 20))
println(p, " ", p[1] == :Point)

Output:

[:Point, 11, 22] true

The example is built to show the deal: dot is the constructor, px/py are the accessories and no function touches the elements by hand except them. If one day you change the order of the fields, you only change the manufacturer and accessories; those who use px and py don't notice this. It's the same principle of encapsulation of a struct, obtained with conventions instead of the type.

22.3 Environment as a list of associations

This is the structure used by user agents in selfhost/: a flat list [name1, value1, name2, value2, …].

function env_get(env, name)
    i = 1
    while i < length(env)
        if env[i] == name
            return env[i + 1]
        end
        i += 2
    end
    nothing
end

function env_set(env, name, value)
    i = 1
    while i < length(env)
        if env[i] == name
            env[i + 1] = value
            return env
        end
        i += 2
    end
    push!(env, name)
    push!(env, value)
end

env = []
env_set(env, :x, 10)
env_set(env, :y, 20)
env_set(env, :x, 11)
println(env, " ", env_get(env, :x), " ", env_get(env, :z))

Output:

[:x, 11, :y, 20] 11 nothing

It's a flat list to avoid paying a level of nesting: the pairs are side by side and env[i+1] reads the value of the name in position i. The cost is that each search is linear and that the two functions must advance two by two; the advantage is that the structure is a normal list, therefore it is printed and inspected without conversions. It's the same pattern an interpreter uses for the environment of names.

22.4 Shared mutable state

Since a named function cannot reassign a global, the shared state is held in one mutable list or in a closure.

status = [0]
function tick()
    status[1] += 1
end
tick()
tick()
println(state[1])

Output:

2

tick does not reassign status: it mutates the list element that status indicates. It's the difference of chapter 3 between changing a link and changing an object, and here is what allows a function appointed to update an external state without violating rule 8.3 on local assignment. The list acts as a container: the state link remains the same, the content changes. If the state must have more fields, you make the list longer (or use a tagged record as in 22.2).

22.5 Constructing strings

Two functions that always return: repeating a string and joining a list with a separator. In Core there is no function that joins a list with a separator, so the separator must be inserted manually, and position is everything: it must be placed in front of every element except the first. Remember that every * creates a new string (chap. 10).

function repeat(s, n)
out = ""
    while n > 0
        out = out * s
        n -= 1
    end
    out
end

function join(xs, sep)
    out = ""
    i = 1
    while i <= length(xs)
        if i > 1
            out = out * sep
        end
        out = out * string(xs[i])
        i += 1
    end
    out
end

println(repeat("ab", 3))
println(join([1, 2, 3], ", "))

Output:

ababab
1, 2, 3

join puts the separator before every element except the first one: this is why the i > 1 check comes first of the two concatenations. If I put it after the element, the last concatenation would leave the separator at the end of the string.

22.6 Style rules

  • Small functions with clear names; explicit base case in every recursion; for great depths prefer while.
  • Loops with explicit counters (i = 1 … while i <= length(xs)).
  • Don't use fact, rule, solve, struct and other Full keywords as names: code must also remain valid in Triad-Full.
  • Write !io on functions that print: Core ignores it, Full requires it.
  • Don't break an expression across multiple lines: the reference interpreter closes the statement at each newlines also inside the brackets (chap. 1.6). One instruction per line.

These rules are not personal tastes: each avoids a concrete problem — a name that collides with Full, an undeclared effect, a reading ambiguity, a broken line that the runtime rejects.

    while i <= strlen(s)
        b = strbyte(s, i)
        if digit(b)
            j = i
            while j <= strlen(s) && digit(strbyte(s, j))

            i = j

        end
    end

end

25. Grammar

Grammar is the most compact form in which a specification says what a valid program is. Yes reads like a recipe: = means «is made of», { … } means «zero or more», [ … ] «optional». The following two grammars do not describe two languages: the first is the subset Core, the second is Full, and the productions that Core shares appear in Full with the same form.

25.1 Triad-Core (EBNF regulation)

program = { sep } { stmt sep { sep } };
sep = NEWLINE | ";" ;
stmt = funcdef | "return" [ expr ] | "break" | "continue" | expr ;
funcdef = "function" NAME "(" [ NAME { "," NAME } ] ")" block "end"
         | NAME "(" [ NAME { "," NAME } ] ")" "=" expr ;
expr = assignment ;
assignment = NAME ( "=" | "+=" | "-=" | "*=" ) expr | ternary ;
ternary = or_expr [ "?" expr ":" expr ] ;
or_expr = and_expr { "||" and_expr } ;
and_expr = cmp_expr { "&&" cmp_expr } ;
cmp_expr = sum_expr { ( "==" | "!=" | "<" | "<=" | ">" | ">=" ) sum_expr } ;
sum_expr = mul_expr { ( "+" | "-" ) mul_expr } ;
mul_expr = pow_expr { ( "*" | "%" ) pow_expr } ;
pow_expr = unary { "^" unary } ;                    (*right*)
unary = ( "-" | "!" ) unary | postfix ;
postfix = primary { "(" args ")" | "[" expr "]" } ;
primary = INT | STRING | SYMBOL | "true" | "false" | "nothing" | NAME
         | "(" expr ")"
         | "[" [ expr { "," expr } ] "]"
         | "(" NAME { "," NAME } ")" "->" expr
         | "if" expr block { "elseif" expr block } [ "else" block ] "end"
         | "while" expr block "end"
         | "let" [ NAME "=" expr { "," NAME "=" expr } ] block "end"
         | "begin" block "end"
| "function" "(" [ NAME { "," NAME } ] ")" block "end" ;
block = { stmt sep { sep } } ;                   (* to end/else/elseif *)

The Core grammar is deliberately small: no for, no ranges, no types in signatures. Not however, it describes every detail that the execution accepts: the assignment to an element (xs[i] = e, xs[i] += e), which the examples in chapter 9 use to mutate lists, does not appear in production assignment. It is a shortcoming of the text of the specification, not of the language: the interpreter of reference supports it, and code using it is portable between Core implementations.

25.2 Triad-Full (EBNF regulation)

program = { sep } { stmt sep { sep } };
sep = NEWLINE | ";" ;
block = { sep } { stmt sep { sep } };

stmt = funcdef | structdef | macrodef | facts | rule
           | "requires" expr | "ensures" expr
           | "return" [ expr ] | "break" | "continue"
           | "(" NAME { "," NAME } ")" "=" expr
           | expr ;

funcdef = "function" fname "(" [ params ] ")" [ "::" TYPE ] [ "!" EFFECT { "," EFFECT } ]
             block "end"
           | NAME "(" [ params ] ")" "=" expr ;
fname = NAME | "+" | "-" | "*" | "/" | "%" | "^" | "==" | "<" | "<=" | ">" | ">=" ;
params = param { "," param } ;
param = NAME [ "::" TYPE ] | "(" NAME { "," NAME } ")" ;
structdef = "struct" NAME sep { NAME [ "::" TYPE ] sep } "end" ;
macrodef = "macro" NAME "(" [ NAME { "," NAME } ] ")" block "end" ;

fact = "fact" term ;
rule = "rule" term [ ":-" goal { "," goal } ] ;

expr = (*Pratt: precedence from lowest to highest *)
  1 a = b a += b a -= b a *= b (right)
  2 x -> e (a, b) -> e c ? a : b (right)
  3 ||
  4 &&
  5 == != < <= > >= in isa is
  6 a:b (range, no spaces)
  7 + -
  8 * / %
  9 -x !x +x $x (unary)
10^ (right)
 11 e::T (type assertion)
 12 f(args) xs[i] a.field (postfixes, no space before ( and [)

primary = NUMBER | STRING | SYMBOL | LVAR | NAME | "true" | "false" | "nothing"
           | "(" expr ")" | "(" expr "," ... ")" (* tuple: lambda parameters *)
           | "[" [ expr { "," expr } [ "|" expr ] ] "]"
           | "[" expr "for" NAME "in" expr [ "if" expr ] "]"
           | ":(" expr ")" | "quotes" block "end"
           | "@"NAME"("args")"
           | "if" expr block { "elseif" expr block } [ "else" block ] "end"
           | "while" expr block "end"
           | "for" NAME "in" expr block "end"
           | "for" "(" NAME { "," NAME } ")" "in" expr block "end"
           | "let" [ NAME "=" expr { "," NAME "=" expr } ] block "end"
           | "begin" block "end"
           | "try" block [ "catch" [ NAME ] block ] "end"
           | "with" modifier { "," modifier } block "end"
           | "solve" goal { "limit" expr | "depth" expr | "steps" expr | "trace" }
           | "function" "(" params ")" block "end" ;

Part I — First steps

1. What is Triad

Triad is a self-contained programming language that brings together three paradigms — imperative, logical and metaprogrammatic — in a single block syntax. The basic idea is that these paradigms should not be kept in separate languages: a Triad program can define functions and loops like an imperative language, declare facts and rules like Prolog, and treat code as a constructible and transformable value as in Lisp, and the three things coexist in the same files without layers or interfaces.

There are three declared influences, and for each one the book will gradually show what Triad has resumed:

influence idea taken up in Triad
Julia function … end, struct, types with ::, multiple dispatch, operators as functions, if/for/while/let
Prolog fact, rule, unification with occurs-check, backtracking, solve with ?x logical variables
Lisp code as given (Node), :( … )/quote with $, macro

To these are added, as part of the language and not of a library: errors as data (Err), contracts (requires/ensures), budget (with budget), tracks (with trace) and declared effects (!io, !state).

The distinction between "part of the language" and "library" is not nominal, and it is worth understanding right away. An error that is a value can be returned, inspected, and composed like any other data, instead of interrupting the program; a written contract in the signature is visible to the implementation, which can control it; a declared effect allows the runtime to verify that a pure function does not print. These are all features that a language can offer only if it knows them, and for this reason Triad defines them in the standard rather than leaving them to conventions between programmers.

From Julia comes the backbone of the syntax: function … end blocks, types with ::, struct and multiple dispatch. From Prolog comes the logic engine: facts, rules, unification with occurs-check, backtracking and solve with logical variables. From Lisp comes the idea that code be a uniform tree, therefore a value like the others, and the macro machine that on that idea leans. Keeping the three models together is the truly new part: it doesn't exist a «Monday language» and a «Tuesday language», there is only one program with only one semantics of expressions and blocks.

1.1 Two profiles: Core and Full

The standard defines two compliance profiles (SPEC §16.1):

  • Triad-Core (SPEC-CORE.md): integers, Bools, strings, symbols, nothing, lists, functions, lambdas and closures, if/elseif/else, while, let, begin, ternary, return/break/continue, plus some bootstrap primitives. It's small enough to be implemented in handwritten machine code and expressive enough to write in the interpreter of all Triad.
  • Triad-Full (SPEC.md): All language.

The separation responds to a practical constraint, not a choice of convenience. The first interpreter of Triad must exist before a Triad compiler exists, so it must be written by hand in code machine: the smaller the language, the more realistic that task is. At the same time the subset must be enough to write the complete interpreter in the second phase. Triad-Core is exactly the point of balance between the two needs, and for this reason it is defined by one specific to itself.

Every Triad-Core program (excluding bootstrap primitives) is also a Triad-Full program valid and must behave in the same way. The reverse is not true: a program that uses struct, for or float is Full, and the Core runtime will not execute it. It is the distinction that you will find in the whole book: Part II teaches the profile going around today, Part III adds the rest.

1.2 The bootstrap chain

Triad doesn't want to depend on any host language, but every language has to start from something. The bootstrap chain solves the problem in stages: We start with an interpreter handwritten in machine code, you use it to run an interpreter written in Triad, e so on up to a compiler that compiles itself. The plan (BOOTSTRAP.md):

S0 seed: Triad-Core interpreter in x86-64 machine code (hex dump in repo)
S1 interpreter of all Triad written in Triad-Core (selfhost/, in progress)
S2 native compiler written in Triad (uninitiated)
S3 self-hosted compiler: S2 compiled by S2 (uninitiated)
S4 Triad complete: REPL, CLI, tooling, parity Linux (not started)

The S0 seed is not distributed as an executable but as a hex dump - that's the simplest way to versioned a binary in a text repository, and materializes with the tool decoding the operating system (chapter 2). Stages S1–S4 are the direction of project, not what you need to read this book: to follow the tutorial all you need is the S0 seed or the JS interpreter.

The tools in Node.js (seed/dev/*.js, conformance/run.mjs, cli/) are ** development**: they help generate and verify, but are not part of the S0→S4 chain. Part IV of the book presents them one by one, explaining what they do and why they are external to the bootstrap.

3. The first program

A Triad program requires no ceremony: there is no configuration file, there are no imports to declare, there is no main function to invoke. The first program is a text file that contains the instructions in the order in which they must be executed.

Create ciao.triad:

#!/usr/bin/env triad
# my first Triad program
name = "Triad"
println("hello, " * name)

Outputs:

42

Run it:

seed\windows-x86_64\seed.exe hello.triad # Windows

What to note:

  • the first line #! (shebang) is ignored: it starts with #, so it is a comment;
  • println prints its arguments without separators and adds a newline;
  • * between strings is concatenation (not +);
  • there is no main function: top level instructions are executed in order.

You can follow the execution line by line. The line name="Triad" evaluates the string and matches that value to the name name. In the following line the runtime reads name, concatenates the two values string with * and pass the result to println. In the last line, 6 * 7 is evaluated first of the call: println gets the integer value 42, not the calculation text. Every instruction is executed only once and in the order in which it appears; a function called can naturally run your body before the program moves on to the next instruction.

The #! line is not a necessary directive for the interpreter: in these examples it is a form conventional useful when the operating system can directly launch an executable file. The Triad runtime ignores it because it treats it as a comment. If an example doesn't work, check separately that the file is saved with a .triad or .td extension, that the command points to the correct runtime and that the source only uses constructs supported by the declared profile.

6. Variables and assignment

A variable, in Triad, is a name tied to a value. You do not declare it or announce its type: the first assignment creates the link, the subsequent ones update it. This makes the code short, but it shifts attention to two questions that in a language with declarations would be automatic: what value is inside a name at this point in the program, and in which environment that name is visible.

The basic rules are these:

  • name = expr binds or updates a name; the assignment is an expression and is the value assigned.
  • +=, -=, *= update an existing variable (the left side is evaluated once).
  • Using a name that was never assigned is an execution error (undefined variable).
  • There are no declarations or types: variables are dynamic.

That the assignment is an expression, and not a statement, is the least obvious rule. It means that x = 42 doesn't "just do something": it produces the value 42, and that value can be used where the assignment appears. In practice it is needed when an assignment appears inside a block which returns a value, but is also why you don't find a hard distinction between «education» and «expression» in the rest of the book. The compound assignment (+=, -=, *=) is sugar for a read and a write of the same variable, with the guarantee that the side claim is evaluated only once: if it contains an index, that index is not calculated twice.

A name used before being assigned is not worth nothing and is not worth zero: it is an error that interrupts the program. It is a deliberate choice, because an implicit "empty" value would hide a logical error; chapter 14 explains how this case is recognized and what you can see it on the terminal.

An expression is a way of combining values to produce another. The negative remainder follows the same logic: -7 % 3 is equal to -1 because the sign is given by the dividend, not the divider. This is the behavior of rem in Julia and should be kept in mind when using % for calculate cyclic positions: with negative values an explicit correction is needed.

8. Flow control

Flow control decides which instructions to execute and how many times. Triad has a constraint that simplifies the mental model: everything is an expression, and so are if, while, let and begin have a value (that of the last executed statement, nothing if none are executed none). There are therefore no two separate worlds — instructions that are worthless ed expressions that are worth something — but only one mechanism, and blocks are expressions that contain other expressions.

8.1 if / elseif / else

function rank(x)
    if x < 0
        "negative"
    elseif x == 0
        "zero"
    else
        "positive"
    end
end
println(rank(-3), " ", rank(0), " ", rank(7))
v = if 2 > 1 :yes else :no end
println(v)

Outputs:

negative zero positive
yes

The if evaluates one condition at a time, from first to last, and executes only the branch corresponding to the first true value; if no conditions are true and an else exists, execute that, otherwise it does nothing and is nothing. elseif is not a sugar for an else which contains another if: it is a branch of the same chain, and this avoids accumulating end a every level. The last line of the example shows that an if can go to the right of a assignment: its value is that of the chosen branch, here the symbol :si.

Two recurring traps: forgetting the end (which closes if, while, function and let) and write else if instead of elseif: in Core elseif is a single branch of the chain, while else if nests a second if and requires an extra end. The ? : from chapter 7 is the compact version of the same scheme, convenient when the two branches are very short expressions.

8.2 while, break, continue

The classic while trap is the order of statements within the body: if continue skips the counter update, the cycle does not end. In the example the counter comes incremented before each continue, and this is no coincidence: the exit condition must be reachable along all paths of the body. break and continue always affect the while innermost, therefore in nested cycles they must be read carefully.

9. Functions

A function is a piece of program that you give a name, with parameters, that returns a value. It is the brick with which everything else is built: in Triad-Core there are no structs either methods, so the function is also the only way to name an operation and reuse it.

9.1 Three ways to define a function

# short form: the body is an expression
square(x) = x * x

# block form: the value is that of the last expression
function compute(n)
    m = n + 1
    m * 2
end

# anonymous function assigned a name
multiply = function (a, b)
    a * b
end

println(square(4), " ", calculate(3), " ", multiply(6, 7))

Outputs:

16 8 42

When compute(3) is called, n receives 3; the body calculates m = 4, then evaluates m * 2 and returns 8 because it is the last expression. The binding m belongs to the call and not automatically becomes a global variable. With the short form, the expression to the right of = it is directly the body. The anonymous function can be given a name, passed as argument or returned by another function: the name is a useful reference, not a property necessary of the function value.

9.2 return, recursion, arity

  • return e exits the function immediately; return alone returns nothing.
  • A named function is visible in its body: direct recursion works.
  • The number of arguments must match the parameters (otherwise arity mismatch).
function size(n)
    if n > 100
        return :large
    end
    :small
end
factorial(n) = n < 2 ? 1 : n * factorial(n - 1)
fib(n) = n < 2 ? n : fib(n - 1) + fib(n - 2)
gcd(a, b) = b == 0 ? a : gcd(b, a % b)
println(size(500), " ", size(5))
println(factorial(10), " ", fib(15), " ", gcd(48, 18))

Outputs:

big small
3628800 610 6

Recursion is understood by following a chain of calls, each with its own parameter. In factorial(4), for example, the call reduces n to 3, 2, and 1; arrived at the base case it returns 1, then the suspended calls resume and multiply the results by 2, 3 and 4. The base case is therefore a termination condition, not a simple additional example. If the parameter does not approaches a base case, the function continues to be called; in the Core runtime the execution budget it is not a language construct, so it is the program's responsibility to avoid recursions unlimited.

Without return, the value of the function is the last expression executed, even when the body ends inside an if. A function is a value bound to a name when the statement of definition is executed: this is why calling it before its definition line produces undefined variable, not an early termination. There are no default arguments either variadic: the arity must coincide exactly with the parameters.

In Core the control does not exist, so the annotation is accepted and ignored: the program runs, but you have no extra guarantee. Writing it right away is still useful, because the code it will be valid when it changes to Full and because it documents the intention of whoever wrote it.

10. Lambdas, closures and scopes

A lambda is a function that doesn't need a name: you write it where you need it, and its value is the function itself. Used whenever you want to pass a behavior to another function — «apply this transformation to each element», «call this check on each value» — without inventing a name that you will only use once. A closure is a lambda that remembers the environment in which it was born; it is the mechanism that makes it possible to construct parametric functions without resorting to global variables.

10.1 Lambda

double = x -> x * 2
sum = (a, b) -> a + b
apply = f -> f(3)
println(double(5), " ", sum(1, 2), " ", apply(x -> x * x))

Outputs:

10 3 9

A lambda with a multi-statement body is written with begin … end or with function (…) … end. Parameterless lambdas (() -> …) are not supported: use function () … end.

10.2 Closures

A lambda captures the environment in which it is created. According to SPEC-CORE §5 the captured variables are shared: mutations are visible.

function add(n)
    x -> x + n
end
f = add(10)
g = add(100)
println(f(5), " ", g(5))

function counter()
    v = 0
    x -> begin
        v += x
        v
    end
end
acc = counter()
acc(5)
println(acc(10))

Outputs:

15 105
15

The Windows seed captures by value and covers only the last binding of the frame: a accumulator as counter may not work on seed (chapter 15).

The difference between an ordinary function and a closure is the external context that remains accessible. add(10) terminates, but the returned lambda retains the n = 10 bond; another calling add creates a distinct environment. In the meter, however, closure is not limited to read v: update the shared binding. The JS interpreter follows the Core contract where this mutation is visible on subsequent calls. The Windows seed has a more limited capture, then a program that depends on this case must be tested with the reference interpreter and not inferred by the mere fact that the seed accepts the syntax.

10.3 Scope rules

  1. function, lambda, let and while introduce environments; a name is visible in the environment in which it is linked and in the internal ones (lexical scope).
  2. Within a named function the assignment binds in the local frame: a function not edit globals.
  3. Inside a lambda the assignment to a name already bound outside updates that binding (this is which works the accumulator above).
  4. At the top level the loops update the globals.
  5. let x = … creates a new x; assigning x inside the let does not affect the outer x.
x = 1
function f()
    x = 2
    x
end
println(f(), " ", x)
c = 0
function increment()
    c += 1
end
increment()
println(c)

Outputs:

2 1
0

The tricky point is that rules 2 and 3 seem to contradict each other: a named function does not modifies a global, a lambda yes. The difference is not capricious, it depends on how they come captured the environments. The lambda brings with it the reference to the environment in which it was created, then the assignment finds the external link and updates it. The named function is intended for be callable on its own, without hidden effects on the names of the global scope: the assignment it creates a local bond, and the global remains what it was. The example shows this with x (which remains 1) and with c (which remains 0 even after increment()).

If you need to communicate a result, there are two paths consistent with this model: giving back the value with return, or put the state in a list, which is mutable and therefore shared also from a named function (chapter 11).

11. Lists

A list is an ordered sequence of values, reachable by position. In Triad-Core it is the working data structure: there are no structs or dictionaries, so lists, lists of lists and lists tagged are how records, environments and trees are represented. Understand how it behaves a list — which is mutable and whose indices start from 1 — is the passage that opens the whole Non-trivial programming in Core.

The basic operations are few, and it's worth reading them thinking about what they do to the list as an object, not just the value they return:

  • Literal: [1, 2, 3], [], heterogeneous and nestable.
  • Indexes from 1: xs[1] is the first element; out of range is an error.
  • Assignment by index: xs[i] = v, also xs[i] += v.
  • length(xs) number of elements; push!(xs, v) appends, mutates the list and the returns.
  • Lists are references: two names can indicate the same list.
xs = [1, 2, 3]
println(xs[1], " ", length(xs))
push!(xs, 4)
xs[1] += 100
println(xs)
alias = xs
push!(aka, 5)
println(xs)
total = 0
i = 1
while i <= length(xs)
    tot += xs[i]
    i += 1
end
println(tot)

Outputs:

1 3
[101, 2, 3, 4]
[101, 2, 3, 4, 5]
115

Core does not have map, filter, reduce, sum, sort: they are written in Core (see chapter 16).

On the Windows seed: lists of integers only, push! yes, xs[i] and length(xs) no; there is instead the non-standard helper get(xs, i) with indices from 0 (chapter 15).

Reference: conformance/core/cases/liste, liste_base, liste_push.

Remember the alias pattern: after alias = xs, the names do not identify two copies, but the same one list. Changing xs[1] or adding an element via alias modifies an observed object from both. If you need an independent value, explicitly construct a new list e you copy the elements with a loop. This behavior is different from an integer variable: assign y = x copies the numeric value and a subsequent reassignment of x does not update y.

In indexed algorithms, the pair i = 1 and i <= length(xs) expresses the complete range of Core positions. Before reading xs[i], make sure i is within that range; an out-of-bounds index is an error, not a nothing element. The case of conformance lists it just checks the standard operations, while the seed's get helper has 0-based and non-0-based indices should be confused with xs[i].

12. Strings, symbols and conversions

Strings and symbols seem like close relatives — they both contain text — but they have roles different. A string is data that is constructed, concatenated and printed; a symbol is a name which the language treats as an atomic value, suitable for labels, keys, record tags, and names of type. Conversions between the two, and between text and numbers, are the bridge needed when a program reads input, constructs messages, or compares values that arrive as text.

The table summarizes the operations available in Core:

To access the individual bytes of a string you need the chapter bootstrap primitives next. Three things deserve attention. First, the strings are immutable: greeting = "hello " * name it doesn't modify "hello ", it constructs a new string. This is consistent with the rest of the language, where only lists are mutable, and makes passing a string to a function harmless: whoever receives it cannot alter it. Second, concatenation uses * and not +: + remains numerical addition, and the choice avoids having to guess the type of operands in an expression like a + b. Third, length counts bytes, not perceived characters: an accented letter can take up two bytes, so in Core “length of a string” means “size in bytes UTF-8", and operations on individual characters are done at byte level with the primitives of chapter 13.

string(x) is a representation meant for reading, not a promise that the result will can read back as source: string(:a) produces "a" (without the colon), and printing a list is not necessarily valid Triad code. For messages it's fine; to rebuild a value are explicit conversions. The conversion is also not a validation: Int("42") assumes that the text is in the right format, and what Int does to text that is not a number is not specified; the program must check first, not hope for a result useful.

The final trap concerns symbols. println(:ok) prints ok, but the value is still a symbol: :ok == "ok" is false, and the correct comparison is with :ok or with Symbol("ok"). The printed appearance of a value is not the value.

13. Bootstrap primitives

They are used by S1 to read and analyze Triad source. They are not part of Triad-Full (SPEC-CORE §8): Use them only in bootstrap code. The name «bootstrap» explains their existence. To write in Triad you need a Triad interpreter the ability to read a file, look at the individual bytes of that file, and extract pieces of it: they are operations that the language does not offer with normal types, because strings are immutable and not indexable. Primitives fill this gap at the lowest possible level, that of gods bytes, and they stay outside the normal language because a complete string library will arrive with S1, written in Triad.

The table lists the five primitives and their semantics:

primitive semantics
readfile(path) file contents as String; error if not readable
strlen(s) number of bytes
strbyte(s, i) bytes (Int 0–255) at position i, from 1
strsub(s, a, b) substring from bytes a to b inclusive, 1
exit(n) terminate the process with code n

All positions are 1-based, like list indices, and strsub includes both extremes: strsub(s, 1, 3) returns the first three bytes. strbyte returns an integer between 0 and 255, not a character: the program must know which codes it is interested in. An index out range is an execution error, not a zero byte; this is why those who analyze a source Always check the limits before reading.

Example: Count the digits of a string and separate the first word.

s = "abc 123 xyz"
digits = 0
i = 1
while i <= strlen(s)
    b = strbyte(s, i)
    if b >= 48 && b <= 57
        digits += 1
    end
    i += 1
end
println(digits)
end = 1
while end <= strlen(s) && strbyte(s, end) != 32
    end += 1
end
println(strsub(s, 1, end - 1))

Outputs:

3
abc

The first loop counts the digits by comparing the byte to the ASCII codes 48–57: strbyte does not says "this is a character", says "this is the number 48", and the program needs to know what 48 is the digit 0. The second loop looks for the first space (code 32) and then strsub extracts the bytes up to the previous one; note that end - 1 can be 0 if the string begins with one space, and it's a case that a real tokenizer needs to handle explicitly.

A program can read itself or another source with readfile(ARGS[1]): that's exactly the first step of a self-hosted interpreter (chapter 37). However, it is worth reiterating the boundary: a program that uses readfile, strlen, strbyte, strsub or exit is not a Valid Triad-Full program. It is one of the few exceptions to the rule «Core is a subset of Full", and that's why these primitives appear in a separate chapter instead of between normal string operations.

14. Execution errors

An execution error is a point at which the program can no longer continue: a name that does not exists, wrong type, index out of range. In Triad-Full the errors are values and yes they can manage; in Triad-Core no, and the difference is important: here an error ends the process with exit code 1 and prints a diagnostic message to stderr. What had already been printed on stdout remains.

Since there is no way to catch the error, the strategy of a Core program is not to "handle" it but «don't provoke him»: check limits before access, convert values before using them, test hypotheses at the beginning of a function. The runtime message is used to understand where it is because the program stopped.

To diagnose an error, separate the level from the program point. If the program prints a first line and then fails, that previous output is not canceled; reproduce minimal case and compare stdout, stderr and exit code separately.

Do not automatically copy the error text produced by a runtime into a test. The suite Core compares stdout and exit code, not stderr: the important contract is the class of behavior declared by the standard. Diagnostic details may change between runtimes, while a return value or output test must remain repeatable.

14.1 Errors as values, in Core

To propagate errors without terminating the process (as S1 will do for Full programs) use a list convention: [:Err, kind, msg].

err(kind, msg) = [:Err, kind, msg]
is_err(v) = typeof(v) == :List && length(v) == 3 && v[1] == :Err
function div_integer(a, b)
    if b == 0
        return err(:domain, "division by zero")
    end
    q = 0
    while a >= b
        a -= b
        q += 1
    end
    q
end
r = integer_div(7, 0)
if is_err(r)
println("error ", r[2], ": ", r[3])
end
println(integer_div(17, 5))

Outputs:

domain error: division by zero
3

The convention [:Err, kind, msg] is not a type of the language: it is a protocol between functions, written with the means that Core offers (lists and symbols). Whoever detects an error builds it with err; whoever receives it must check the tag before reading the fields, and this is why is_err exists. The advantage is that the error travels like any other value: it can be returned, saved, compared, printed. The limit is that nothing forces a function to respect the protocol: if it returns a normal list, the tag check fails and the program continues with the wrong value.

When S1 executes Triad-Full, the language will have true Err values (chapter 24) and this convention will become superfluous; in the meantime it's the way to do it living with "error as given" with a runtime that doesn't allow for it.

16. Triad-Core Idiomatic Patterns

Previous chapters have explained the individual constructs; this brings them together in some recurring patterns. They are not the only way to write Triad-Core, but they are the ways in which the language is actually used in the repository, including the S1 code in selfhost/. Recognizing them helps you read other people's code and choose a structure when you don't already have one one in mind.

16.1 Higher-order functions written in Core

Core has no map/filter/reduce: they are written once with while and lambda.

function map(f, xs)
    out = []
    i = 1
    while i <= length(xs)
        push!(out, f(xs[i]))
        i += 1
    end
    out
end
function filter(p, xs)
    out = []
    i = 1
    while i <= length(xs)
        if p(xs[i])
            push!(out, xs[i])
        end
        i += 1
    end
    out
end
function reduce(f, acc, xs)
    i = 1
    while i <= length(xs)
        acc = f(acc, xs[i])
i += 1
    end
    acc
end
xs = [1, 2, 3, 4, 5, 6]
println(map(x -> x * x, xs))
println(filter(x -> x % 2 == 0, xs))
println(reduce((a, b) -> a + b, 0, xs))

Outputs:

[1, 4, 9, 16, 25, 36]
[2, 4, 6]
21

These three patterns show that higher order functions do not require support syntactic: a function receiving another function is already possible, and while is enough for scroll through the list. map builds a new list, filter decides element by element, reduce brings forward an accumulator. They are also the starting point when your program must transform data without the conveniences of Triad-Full.

16.2 Records as tagged lists

Core has no struct: a record is a list with a symbol as a tag in the first position.

point(x, y) = [:Point, x, y]
px(p) = p[2]
py(p) = p[3]
sum_points(a, b) = point(px(a) + px(b), py(a) + py(b))
p = sum_points(point(1, 2), point(10, 20))
println(p, " ", p[1] == :Point)

Outputs:

[:Point, 11, 22] true

The tag is not decoration: it is the discriminant that allows us to recognize the type of record a runtime and write functions like px and py that take a precise form. In Full the same role will be of the struct (chapter 20), with the advantage of field control; in Core the tagged list gives the same structure without that control, and it's up to the programmer comply with the convention.

16.3 Environment as a list of associations

This is the structure used by user agents in selfhost/: a flat list [name1, value1, name2, value2, …] (in Core you can also use nested pairs).

function env_get(env, name)
    i = 1
    while i < length(env)
        if env[i] == name
            return env[i + 1]
        end
        i += 2
    end
    nothing
end
function env_set(env, name, value)
    i = 1
    while i < length(env)
        if env[i] == name
            env[i + 1] = value
            return env
        end
        i += 2
end
    push!(env, name)
    push!(env, value)
end
env = []
env_set(env, :x, 10)
env_set(env, :y, 20)
env_set(env, :x, 11)
println(env, " ", env_get(env, :x), " ", env_get(env, :z))

Outputs:

[:x, 11, :y, 20] 11 nothing

The flat list alternates name and value: env_get advances two positions, env_set updates if finds the name and otherwise adds to the queue. The while i < length(env) (not <=) is deliberate: the last useful position is length(env) - 1, because env[i + 1] must remain inside the list. It's the same structure that makes an interpreter written in Core possible: environments are given like the others, not a hidden mechanism of language.

16.4 Shared mutable state

Since a named function cannot reassign a global, the shared state is held in a (mutable) list or in a closure.

status = [0]
function tick()
    status[1] += 1
end
tick()

2

The list acts as a shared cell: the named function cannot reassign state, but it can change the object that state points to, and the mutation remains visible outside. It's the most way simple to get mutable state in Core without closures; the closure (chapter 10) is the alternative when the state must remain private.

16.5 Constructing strings

function repeat(s, n)
    out = ""
    while n > 0
        out = out * s
        n -= 1
    end
    out
end
function join(xs, sep)
    out = ""
    i = 1
    while i <= length(xs)
        if i > 1
            out = out * sep
        end
        out = out * string(xs[i])
        i += 1
    end
    out
end
println(repeat("ab", 3))
println(join([1, 2, 3], ", "))

Outputs:

ababab
1, 2, 3

Building a string by successive concatenations is correct but expensive: each * creates a new one string, then the loop constructs as many intermediate strings as there are iterations. In Core there are no better alternatives — there is no support structure — and for the programs of studying is fine; in a real interpreter it is better to accumulate the pieces in a list and join them together only once at the end.

16.6 Style

The following rules are not aesthetic: they arise from the fact that the code itself may have to switch to Triad-Full and that the repository is written in Italian.

  • Small functions with clear names (in Italian, as in the rest of the repository).
  • Explicit base case in every recursion; for large depths prefer while.
  • Loops with explicit counters (i = 1 … while i <= length(xs)).
  • Don't use fact, rule, solve, struct and other Full keywords as names: the code must also remain valid in Triad-Full.
  • Write !io on functions that print: Core ignores it, Full requires it.

They are conventions, not rules of the language: the runtime does not control them. But a program that respect remains valid both in Core and in Full, and this is the quality that makes the code of reusable project in subsequent bootstrap stages.

19. Typed and multiple dispatch functions (SPEC §5)

area(n::Number) = :number
area(n::Int) = :int

function dist(a::Point, b::Point)::Float
    requires a.x != b.x || a.y != b.y
    sqrt((a.x - b.x)^2 + (a.y - b.y)^2)
end

function +(a::Point, b::Point) # operators are redefinable functions
    Point(a.x + b.x, a.y + b.y)
end

Rules:

  • the most specific method among the applicable ones wins (area(1) == :int, area(1.5) == :number);
  • no applicable methods → Err(:method) (or builtin fallback for numeric operators);
  • multiple equally specific methods → Err(:ambiguous);
  • the ::R return type is checked at output (with Int→Float conversion);
  • functions and operators are values: reduce(+, xs), map(sq, xs);
  • lambda type: function (x::Int) x end → f(2.0) is Err(:type).

To predict which implementation will be called, first check the number of arguments and then the type of each. With the area(n::Number) and area(n::Int) methods, the integer 1 is compatible with both, but Int is more specific than Number; the Float 1.5 is only compatible with the method on Number. In methods with multiple parameters the comparison is per tuple: a signature can be more specific on the first parameter but more general on the second. If no signature dominates all others, you can't guess the intent: the result is the :ambiguous error, which requires a signature more specific or a revision of existing signatures. The control of the return type occurs after the body. This is why ::Float does not convert them arguments in advance and does not guarantee that every intermediate operation is valid; requires that the value produced in the end is convertible or compatible with the declared type. The annotations parameter and return are therefore distinct parts of the method contract.

22. Logic: facts, rules, solve (SPEC §6)

fact parent(:alice, :bob)
fact parent(:alice, :carol)
fact parent(:bob, :dave)

rule grandparent(?x, ?z) :- parent(?x, ?y), parent(?y, ?z)
rule ancestor(?a, ?d) :- parent(?a, ?d)
rule ancestor(?a, ?d) :- parent(?a, ?x), ancestor(?x, ?d)

solve returns a list of Solution (it's a value, it doesn't print anything):

sols = solve grandparent(:alice, ?who) limit 5
[s.who for s in sols] # [:dave]
[s.d for s in solve ancestor(:alice, ?d)]
  • Options: limit n, depth d, steps s (default 1 000 000), trace.
  • A predicate used as a function is a Bool: grandparent(:alice, :dave) → true; can be used in if.
  • Goal: p(t…), g1 && g2, (g1, g2), g1 || g2, !g/not(g), a = b (unification), ?y is expr, comparisons, Triad function returning Bool, true/false.
  • Occurs-check active: solve ?x = f(?x) has no solutions (does not loop).
  • Prolog style lists in patterns: [?h | ?t].
  • vars(s) returns the names bound in a Solution; accessed with s.name or s[:name].

To read a rule, separate the head from the body. In grandparent(?x, ?z) :- parent(?x, ?y), parent(?y, ?z), the head describes what values the rule can demonstrate; the body requires two tests in sequence. The engine searches for a parent for the first goal, keep the found binding for ?y, then use that binding in the second goal. If the second goal fails, go back to the previous choice and try the next compatible fact: it is the backtracking. If both succeed, ?z is returned in the solution.

Variables with the same name in different clauses do not accidentally share theirs status: each time the rule is used they are renamed. Occurs-check prevents recursive bindings impossible like ?x = f(?x). The depth limit cuts branches that are too deep; steps limits the total work; limit limits how many solutions are collected. They are different controls, e.g an empty list obtained within bounds is not equivalent to a search interrupted by Err(:budget).

List pattern with exact arity; the brackets around the pattern are mandatory.

24. Errors as data (SPEC §8)

An error is an Err(kind, msg, data) value; does not become a host exception unless is managed at the top level (then the process exits with code 1 and stdout empty for the instruction failed: this is the case of conformance error).

e = try div(1, 0) end # Err(:domain, ...)
e.kind # :domain
e.msg # message
iserr(e) # true
7.0 / 0 # Inf: Float division is not an error
throw(err(:my, "oops", 42))
error("boom") # Err(:error, ...)

describe(e::Err) = string("error ", e.kind, ": ", e.msg)
describe(x::Any) = string("value ", x)
for r in [try div(10, d) end for d in [2, 0, 5]]
println(describe(r))
end

Standard Kinds: :syntax, :undef, :type, :method, :ambiguous, :field, :bounds, :domain, :instantiation, :contract, :budget, :effect, :host.

Err(:syntax) brings the position (e.data.line, e.data.col) to data.

Error handling separates the failed operation from the point at which the program decides how react. try does not automatically repair the state: it converts the outcome to an Err or value pass that value to the catch block. The caller can then choose between showing a message, try an alternative or propagate the error by returning it. If no try intercepts it, the runtime reports this to the upper level and the process ends with failed code. In this way the management is explicit, but a mistake does not become a success just because it is represented by a value.

25. Contracts (SPEC §9)

function safe_div(a::Number, b::Number)::Float
    requires b != 0
    ensures abs(result * b - a) < 1e-9
    a/b
end

safe_div(6, 3) # 2.0
e = try safe_div(1, 0) end
e.kind # :contract
e.data.clause # :requires
e.data.fn # :safe_div
  • requires c is checked where it appears (beginning of the body, or at the top level as an assertion).
  • ensures c is checked on exit, with result tied to the return value, after the return type control.
  • Violation → Err(:contract, …) with data.clause, data.fn, data.cond, data.result.
  • Contracts are pure: an effect inside a contract → Err(:effect).
  • ensures outside function → Err(:syntax).

Think of requires as the entry condition of the operation and ensures as the exit condition. A precondition specifies what the caller must guarantee; one postcondition specifies what the function promises when it finishes successfully. The clauses they do not replace type checking: a function can receive arguments of the right type and violate a domain precondition anyway, or return a typed value that violates the postcondition. Since contracts are pure, their evaluation cannot print or modify the knowledge base: the check must not change the program it is checking.

26. Budget (SPEC §10)

r = with budget(steps = 10_000)
    while true end
end
r.kind # :budget — infinite loop becomes a value
  • One step = one call, one loop iteration, one resolution step.
  • Budgets are nested: the tightest applies; only the budget of the current with becomes value, the external one propagates.
  • solve … steps N is the budget of a single query.
  • Infinite recursion doesn't stack overflow: it ends in Err(:budget) (explicit stack).

The budget measures standard-defined units of work, not seconds of CPU and not memory allocated. It is therefore a reproducible limit on the number of steps of the execution model, not a general operating system timeout. Use this to potentially limit computations long, especially logical resolution or a loop that may not finish. The result Err(:budget) is distinct from the valid result body and can be handled with try or the checking the value returned by the with.

27. Tracks (SPEC §11)

Trace is a value, not output.

fib(n::Int) = n < 2 ? n : fib(n - 1) + fib(n - 2)
t = with trace
    fib(3)
end
t.result #2
t.trace # [Event(port=:call, fn=:fib, args=[3], depth=0), …]

t = solve path(:a, :c) trace
t.trace # Byrd ports: :call, :exit, :redo, :fail, :depth

Events are records with port, goal/fn, depth (and value/args for functions): they filter like any value. The trace records the history of the calculation, not just its result. In a function trace call indicates entry and exit indicates exit; redo and fail also appear in a logical query, because research can test multiple alternatives. The result value remains available next to the events: you can compare the final result with the path followed. The trace is not a log automatically printed; the program decides which events to filter, count or present.

28. Declared effects (SPEC §12)

The functions are pure by default. Effects: io (println, print) and state (fact/rule inside a function).

function hello(name::String) !io
    println("hello, ", name)
end

function learn(x) !state
    fact seen($x)
end
  • Dynamic control: a pure function that calls an !io or println → Err(:effect).
  • The top level allows all effects; lambdas inherit those of the context.
  • Macros and contracts are pure; reading the KB (solve, predicates) is pure.
  • Mutating lists or local variables is not an effect.

The effect declaration is a dynamic check of execution permissions, not an annotation purely descriptive. The runtime checks the call chain when a function tries an operation with effect: an !io function can print only if the calling context lo allows. The top level is the most permissive context; a pure function called from there does not become therefore authorized to print. Listing !io in the signature documents the requirement for i callers and allows the runtime to reject the effect at the point where it would violate the declaration.

29.3 Macros

Macros receive code and return code; the expansion is pure and unhygienic: use gensym() for fresh names.

macro unless(c, body)
    :(if !$c; $body; end)
end

macro swap(a, b)
    tmp = gensym(:tmp)
    odds
        $tmp = $a
        $a = $b
        $b = $tmp
    end
end

macro time_it(label, e)
    :(begin
        r = $e
        println($label, " -> ", r)
        r
    end)
end

@swap(x, y)
@unless(x < y, println("x is not less than y"))
@time_it("sum", reduce(+, 1:100)) # print "sum -> 5050"

To evaluate a macro, compare the source argument to the code it builds. In @unless(c, body), c and body arrive as nodes; the macro puts them in an if with the denied condition. The body will only run if the original condition is false, just like if the programmer had written that code manually. If the macro used a function Ordinary, the arguments would be calculated before the call and this would not be possible check if body is evaluated. This ability is powerful, but it makes reading more difficult execution: Explicit expansion and generated temporary names are essential tools for avoid surprises.

34.1 Architecture

source ──tokenize()──▶ token ──Parser──▶ AST {kind: …} ──evalStmt/evalExpr──▶ effects on stdout
  1. Values (top of file): {t, v} objects constructed from I (Int, BigInt with wrap() (64-bit), B, S, Y (Symbol), L (List), F (function: params, body, env, isLambda) and the constant NOTHING. Builtins are {t:'builtin', name}.
  2. tokenize(src): produces tokens SEP (newline or ;), NUM, STR, SYM, IDENT, OP, LPAREN/RPAREN, LBRACKET/RBRACKET, COMMA, QMARK, COLON, EOF. Comments and spaces they are discarded here.
  3. class Parser: recursive descent that follows the precedence of §7.1: parseProgram → parseStmt → parseExpr → parseAssign → parseTernary → … → parsePostfix → parsePrimary, plus parseBlock(terminators) for bodies up to end/else/elseif. Product nodes: program, funcdef, return, break, continue, exprstmt, num, str, sym, bool, nothing, var, list, lambda, assign, indexassign, binary, unary, ternary, call, index, if, while, let, begin.
  4. Environments: makeFrame(parent, owner, isLambda) creates a frame with a Map of bonds; lookup goes up the chain. writeVar implements the scope rules of §10.3: updates a binding of the same "owner" (function), or, inside a lambda, a external bond; otherwise create a room.
  5. Evaluation: evalStmt, evalExpr → evalExprBinary → evalExprRest → evalExprBlocks. return, break, continue are JS exceptions (ReturnSignal, BreakSignal, ContinueSignal) captured by the call or while.
  6. Builtin: set BUILTIN_NAMES + callBuiltin(name, args, env); print with printValue (symbols without : only at top level) and conversion with stringOf.
  7. main(): read file (or stdin with -), bind ARGS, execute; parsing errors → parse error: …, execution errors → error: …, both with exit 1; no files → exit 2.

This flow separates responsibilities that are best diagnosed one at a time. If the token produced by tokenize is wrong, the problem is before the parser; if the parser generates the shape incorrect, the AST tree does not match the grammar; if the tree is correct but the result is not, the flaw is in the environment, evaluation or a builtin. A small conformance case allows you to fix the observed behavior while correcting the responsible level. When you change syntax or semantics, the test, the interpreter and the specification must remain consistent: adding a branch to the parser without corresponding evaluation creates a recognized shape but not executable.

34.2 Example: Adding a builtin

Suppose we want to experiment with an abs builtin (it is not in Core: it must first be proposed in the standard, see §43). Two changes are needed:

// 1. record the name
const BUILTIN_NAMES = new Set(['print','println','length','push!','Int','string','Symbol',
  'typeof','readfile','strlen','strbyte','strsub','exit','abs']);

// 2. implement it in callBuiltin, before the final throw
  if (name === 'abs') {
    if (args.length !== 1 || args[0].t !== 'int') throw new Error('abs');
    return I(args[0].v < 0n ? -args[0].v : args[0].v);
  }

Then: a case in conformance/core/cases/ (§38) and node conformance/run.mjs. Remember that Int are BigInt (0n, 1n) and that the results must be constructed with helper (I, B, S, Y, L, NOTHING).

34.3 Example: Add syntax

  1. if you need a new token, extend tokenize (e.g. an operator in twoOps);
  2. add the precedence level in the Parser producing a new kind;
  3. handle kind in evalExpr*;
  4. update SPEC-CORE.md (grammar §4 and semantics §5) and add a Core case.

Rule: JS interpreter must remain faithful to SPEC-CORE; do not add extensions that the seed and S1 should not have.

35. The S0 Windows seed and its generator

35.1 What is it

seed/windows-x86_64/seed.exe is a 25,088 byte x86-64 PE32+ that only imports KERNEL32.dll (GetStdHandle, GetCommandLineA, CreateFileA, ReadFile, WriteFile, CloseHandle, ExitProcess, VirtualAlloc). It doesn't use libc or runtime. The source is the dump seed.hex (SHA-256 verified by CI: 3A75A21E2F47D8DC4C88D4BC2580A85D5349BCDF7550E5FFA16E2C0AC7CA8C11).

The seed does not build an AST: it interprets the source text directly, with a cursor (rsi) which iterates through bytes; function bodies and lambdas are pointers to the source they come from re-executed for each call.

35.2 Internal conventions

register role
r14 memory base VirtualAlloc (source at +0, environment at +0x10000, functions at +0x20000, heap at +0x30000)
r15 environment variables (24 byte entry: name ptr, len, value)
rbx variable counter
r13 function table (128 byte entry)
r12 stdout handle
rsi cursor in source

2-bit tagged values: Int = n << 2, false = 1, true = 5, closure = ptr | 2, objects heap (strings [type][len][byte…]) with tags 3. The complete layout (PE header, IAT, map of the labels parse_program, st_if, parse_primary, env_find, …) is in seed/windows-x86_64/README.md.

35.3 The seed/dev/gen_seed.js generator

Writing thousands of bytes by hand is impractical: the generator is assembler-lite in JavaScript that outputs bytes and resolves labels. File sections:

section what
emitter B(...) outputs bytes, B32(v) a dword, L(name) defines a label, reloc/je/jne/jmp/callL outputs jumps with relative patches, callIat(i) calls the import i
instruction helper functions with the instruction name (incRsi, cmpByteRsiImm('('), testRax, leaRdxR14(d), …) that output the corresponding x86-64 bytes
PE/data layout constants IAT = 0x4000, SEC_RAW, HEADERS
main prologue, reading the command line, opening/reading the file
parser the heart of the interpreter: statements, expressions, functions, lambdas
environment env_find, env_store, env_assign
exit labels fail, read_fail, open_fail, usage
PE builder writes DOS/PE/COFF header, .text section, import tables, and hex dump

Style example (from main): Skip the program name on the command line.

cmpByteRsiImm(0x22); jne('skip_plain');   // the path begins with " ?
L('q_loop');
incRsi();
cmpByteRsiImm(0); je('no_arg');           // end of string: no arguments → exit 2
cmpByteRsiImm(0x22); jne('q_loop');

35.4 Flow to modify the seed

  1. edit seed/dev/gen_seed.js (add a label, a branch in the dispatcher, …);
  2. regenerate the dump: node seed/dev/gen_seed.js seed/windows-x86_64/seed.hex (or bin/triad-cli seed generate windows, which also prints SHA-256);
  3. decode on Windows: certutil -decodehex -f seed\windows-x86_64\seed.hex seed\windows-x86_64\seed.exe;
  4. run the Core cases on the test_get.td seed and probe;
  5. update together: hash in .github/workflows/ci.yml (job seed-windows, step Hash check), seed/windows-x86_64/README.md, seed/dev/README.md, STATUS.md; if a new Core case passes on the seed, add it to the job's $cases array.

Known traps (from STATUS.md): code grows and can overlap data (names import now start from RVA 0x5000); registers used before being initialized (pbs_int bug); order of arguments on the stack in builtin (get) calls. Defender can report the PE as false positive (CI adds an exclusion).

37.1 How to write S1 code today

The S1 code must run on the Windows seed, so it follows the restrictions in the right column of chapter 15:

  • use get(xs, i) with indices from 0 instead of xs[i] (non-standard: should be replaced with Core indexing when the seed supports it);
  • lists of integers only: the source strings are represented as lists of ASCII codes, with the length in position 0;
  • push! returns the list: write env = push!(env, v);
  • constants for token types (0 EOF, 1 NUMBER, 2 IDENTIFIER, …) documented in a comment at the top of the file;
  • functions with at most 4 parameters, one-parameter lambda, no multi-binding capture.
# S1 style: flat environment and lookup with get (0-based)

env = push!(env, 10) # value

  println("Value: " * string(get(env, 1)))

38. Conformance: Read, write and verify cases

38.1 Format

conformance/core/cases/<name>/ (or conformance/cases/<name>/ for Full)
  program.td Triad program executed as a script
optional args.txt: one argument per line (ARGS)
  expected.out stdout expected, byte by byte, end of line LF
  expected.golden copy of expected.out (runner fallback)
  expected.code exit code expected

A case passes if stdout and exit code match; stderr is not matched. No stdin nor interactive input.

38.2 The conformance/run.mjs runner

node conformance/run.mjs # Core (default conformance/core/cases)
node conformance/run.mjs --cases conformance/cases # Full (only error passes today)
node conformance/run.mjs --skip lists,values # skip cases (default: lists)
node conformance/run.mjs --update # REGENERATE goldens from the current runtime

Runtime chosen, in order: variable TRIAD_SEED; on Linux/macOS the JS interpreter; on Windows bin/triad-native.exe, then seed/windows-x86_64/seed.exe. Example to test the seed with a explicit path: TRIAD_SEED=/path/seed node conformance/run.mjs.

On Linux/macOS the runner uses the JS interpreter and checks all 37 cases. On Windows use seed e skips the lists case by default, because the seed does not implement indexing standard xs[i]: the runner then prints 36 cases. To test the excluded case with the JS interpreter:

node seed/dev/triad_core.cjs conformance/core/cases/liste/program.td

Messages:

  • PASS name / FAIL name (exit X, expected Y, stdout N bytes, expected M);
  • golden missing: checkout does not have expected.out (usually git pull is enough).

A golden is a versioned expectation, not the normative source of semantics. The file program.td defines the input, args.txt the arguments, expected.out the byte-by-byte output, and expected.code the exit code. The runner compares these results with the chosen runtime; thus the same case can be performed by multiple interpreters and make the divergences visible. If runtime behavior is in doubt, first compare the case with SPEC-CORE and then fix the golden only when the specification confirms the new expected value. The --update option copies the current behavior in the expected results: using it without review would turn a bug into a claim of correctness.

38.3 Add a Core case

  1. choose a descriptive name in Italian (liste_nested, stringhe_vuote, …);
  2. write program.td using only SPEC-CORE §2–§7 (no bootstrap primitives: they must also turn on Full);
  3. write expected.out (with final LF) and expected.code (0) by hand, reasoning about the specify — don't blindly generate them with --update, otherwise you'll fix runtime bugs;
  4. copy expected.out to expected.golden;
  5. node conformance/run.mjs should print PASS <name>;
  6. if the case also passes on the Windows seed, add it to $cases in the seed-windows job of .github/workflows/ci.yml.
mkdir conformance/core/cases/sum_list
cat > conformance/core/cases/somma_lista/program.td <<'TD'

total = 0
i = 1

    tot += xs[i]
    i += 1
end
println(tot)
TD
printf '12\n' > conformance/core/cases/sum_list/expected.out
cp conformance/core/cases/somma_lista/expected.out conformance/core/cases/somma_lista/expected.golden
printf '0' > conformance/core/cases/sum_list/expected.code

44. Triad-Core Grammar (EBNF)

From SPEC-CORE.md §4:

program = { sep } { stmt sep { sep } };
stmt = funcdef | "return" [ expr ] | "break" | "continue" | expr ;
funcdef = "function" NAME "(" [ NAME { "," NAME } ] ")" block "end"
         | NAME "(" [ NAME { "," NAME } ] ")" "=" expr ;
expr = assignment ;
assignment = NAME ( "=" | "+=" | "-=" | "*=" ) expr | ternary ;
ternary = or_expr [ "?" expr ":" expr ] ;
or_expr = and_expr { "||" and_expr } ;
and_expr = cmp_expr { "&&" cmp_expr } ;
cmp_expr = sum_expr { ( "==" | "!=" | "<" | "<=" | ">" | ">=" ) sum_expr } ;
sum_expr = mul_expr { ( "+" | "-" ) mul_expr } ;
mul_expr = pow_expr { ( "*" | "%" ) pow_expr } ;
pow_expr = unary { "^" unary } ;                    (*right*)
unary = ( "-" | "!" ) unary | postfix ;
postfix = primary { "(" args ")" | "[" expr "]" } ;
primary = INT | STRING | SYMBOL | "true" | "false" | "nothing" | NAME
         | "(" expr ")"
         | "[" [ expr { "," expr } ] "]"
         | "(" NAME { "," NAME } ")" "->" expr
         | "if" expr block { "elseif" expr block } [ "else" block ] "end"
         | "while" expr block "end"
         | "let" [ NAME "=" expr { "," NAME "=" expr } ] block "end"
         | "begin" block "end"
         | "function" "(" [ NAME { "," NAME } ] ")" block "end" ;
block = { stmt sep { sep } } ;                   (* to end/else/elseif *)

The Full grammar (Pratt, 12 levels) is in SPEC.md §2.

49. FAQ

Do you need Julia? No. The Julia implementation has been removed; Triad runs on the coded seed machine (Windows) or on the development JS interpreter.

Why don't my examples with struct or fact run? I'm Triad-Full: the current runtime runs Triad-Core only. See the profile table at the beginning of the Tutorial.

.td or .triad? .triad is canonical; .td is accepted as an alias (and is also the LLVM TableGen extension, so .triad is better for external recognition).

How do I check if a program is "pure" Core? Run it with the JS interpreter and check not to use bootstrap primitives if this also applies to Full; for regulatory cases add it to the Core conformance.

Why do selfhost/*.td fail with JS interpreter? They use get(xs, i), helper not Windows seed standard; they must be executed with seed.exe.

Where do I propose a change to the language? In the standard (SPEC.md/SPEC-CORE.md) with entry in CHANGELOG.md and conformance cases; then in the implementations.

The Book of Triad

Triad 2.0 is an autonomous programming language, defined by a specific regulation independent of any implementation. It is not a dialect of Julia, Prolog or Lisp, despite having taken from each of them fundamental ideas: function … end blocks and types with :: from Julia, unification with occurs-check, backtracking and solve with ?x logical variables from Prolog, code as data and macros from Lisp. What is proper of Triad, and not borrowed, is the integration of the three models — imperative, logical, metaprogramming — in a single block syntax, accompanied by errors as data (Err), contracts (requires/ensures), budget (with budget), traces (with trace) and declared effects (!io, !state) as part of the language and not a library.

The language comes in two conformance profiles. Triad-Core is the subset of bootstrap: values, functions, closures, flow control, lists, strings, I/O. Triad-Full is the complete standard: declared types, multiple dispatch, integrated logic, macros, contracts, budget, tracks, effects. Every Core program is also a valid Full program and must behave the same way. The JavaScript reference interpreter runs Triad-Core; the S0 Windows seed is a distinct and more limited x86-64 machine code interpreter. The current Linux seed is still an E0 boot test, not an interpreter. The bootstrap plan involves S1 (an interpreter Triad written in Triad-Core), S2 (native compiler), S3 (self-hosting), and S4 (cross-platform parity).

This book is the study path of the language as it is defined by the standard. The Manual and Tutorial alternate conceptual explanations, technical semantics, annotated examples, exercises and references to the specification. Each text presents concepts where they are needed and distinguishes constructs executable today from those defined by the standard but not yet supported. The Tutorial first accompanies the reader in the Core constructs executable today, then presents Triad-Full as a standard to study and finally shows how to read the implementations, the bootstrap and conformance suite in the repository. Block labels distinguish the code executable from code defined by the standard but not yet supported by the runtime.

The project is released under the MIT license. The specific regulation is in SPEC.md (standard 0.2.0), the bootstrap subset in SPEC-CORE.md, the conformance suite in conformance/ with verifiable golden. The repository also includes a benchmark for the build of Triad code from LLM (ai/), grammars for VS Code and Vim, and a site with the learning. The goal is an autonomous and recognized language: own standard, conformance executable, .triad extension, tooling editor, bootstrap without guest languages and, finally, self-hosting.

The conformance suite is the executable contract of the language. The reference interpreter JavaScript passes all 37 Core cases; the Windows seed passes supported cases and leaves out by default the liste case, which requires standard indexing. The Linux seed is still at the E0 stage and only prints a startup message. The Full profile is defined by standard, but the current runtime does not yet implement the complete language; the outputs labeled golden are expected results stored in the suite files. Each Core case states output and exit code, so that an implementation can be compared to a contract reproducible, not with an isolated example.

Editor tools include grammars for VS Code and Vim/Neovim and an entry for GitHub Linguist, so that the .triad (canonical) and .td (historical alias) files are recognized everywhere. The project website exposes the learning curve, the graphs of the steps and an animated demo of typing a Triad-Core program executed by the interpreter. The repository is organized to be explored: progressive examples in examples/, guided tasks in ai/tasks/, LLM benchmarks in ai/. Every change is accompanied by tests and updates to STATUS.md, BOOTSTRAP.md and CHANGELOG.md.

This book is written for the 0.2.0 standard. In case of discrepancy between manual and specification, specification prevails: SPEC.md and SPEC-CORE.md are the source of normative truth, and this volume is the study path, with explanations, examples and exercises.
