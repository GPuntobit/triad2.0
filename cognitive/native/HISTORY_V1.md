# TRID-015 — Historical memory views and revision diff (v1)

**Status:** version-scoped read-only queries over the committed TRID-011
event ledger and the native TRID-012 projection. These commands are **not**
proof of external truth and do not promote experimental knowledge.

## API

From the repository root on Linux x86_64 with the Triad seed installed:

```sh
TRID_EVENT_STATE_DIR="$HOME/trid-events-v2" \
  sh cognitive/native/history_v1.sh --as-of r00000001 > memory-at-1.view

TRID_EVENT_STATE_DIR="$HOME/trid-events-v2" \
  sh cognitive/native/history_v1.sh --diff r00000001 r00000002 > changes.diff

TRID_EVENT_STATE_DIR="$HOME/trid-events-v2" \
  sh cognitive/native/journal_v1.sh --replay-revision r00000001 > events-at-1.v1

sh cognitive/native/tests/run_history_v1.sh
```

A revision is the ledger's **committed generation** `rNNNNNNNN`, not
the numeric per-entity revision field inside a v1 event. Both revisions
must exist and be ancestors of the currently committed head. A missing,
future, malformed or divergent archive is rejected. No historical
snapshot is generated by extrapolating a missing state.

`--as-of` replays the selected generation's validated record stream
and invokes the existing **native Triad-Core** `--project-current`
fold. It emits the most recent record per ID and the effective
suspension state resulting from explicit revocations already recorded
by that generation. A later revocation cannot change an older view.
A source missing from a later input does not constitute a revocation.

`--diff` computes a deterministic unified text diff of the two native
views (in ledger/order-of-last-revision order). A changed `source`,
`assumptions`, `dependencies`, origin event, epistemic state or payload
is visible as removed/added record lines. This is a **byte-level
comparison of native views**, not a separate semantic inference
algorithm, calibrated confidence judgment or source-authenticity check.
Identical views produce empty output and exit 0; different views also
exit 0; invalid input or corruption exits nonzero without publishing
partial stdout.

## Read consistency and integrity

`journal_v1.sh --replay-revision` acquires the existing permanent
ledger `flock`, verifies the active pointer and head manifest, verifies
the archived generation's manifest, and checks that the archived
**full chained bytes** are a prefix of the active committed stream.
It then validates *every* selected event's sequence, predecessor hash,
SHA-256 digest and native schema/revision constraints. A corrupted or
rewritten archive cannot be silently substituted for a different
historical state merely by recalculating its manifest, unless an
attacker also rewrites the trusted current head and its chain.

The lock protects extraction of **one** consistent replay; the two
`--diff` endpoints are independently verified, not acquired under
a single cross-query lock. A concurrent append could add a new head
between the two extractions but cannot alter either immutable ancestor.
The commands do not change the active pointer or committed data.
As before, SHA-256 is not a signature and local administrators with
full write control are outside the tamper-resistance guarantee.

## Verification scope

`run_history_v1.sh` covers past views remaining byte-exact after
new appends, a source-specific revocation affecting only dependent
facts, an explicit source/provenance revision, stable diffs, rejected
future and malformed generations, divergent/re-hashed archive data,
concurrent lock rejection and current-pointer preservation. It is run
from the native S0 CI suite, on the same candidate SHA as the other
TRID Required checks.

**Limits:** the ledger retains full copy-on-append generations;
reading old generations requires disk space for historical files and
native bounded-window replay. This is not an arbitrary historical query
language, distributed transaction across S0/S1 and ledger stores,
or native direct-write API for the S0 seed. Those remain separate work.
